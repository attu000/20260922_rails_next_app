# ハロー・インターン（仮）：インターン×企業 スカウトサービス（プロトタイプ）

エンジニア職の長期インターンを探す学生と、学生を探す企業をつなぐ「募集・スカウトサービス」のプロトタイプです。


## 進め方
1. まず、AIと人間で設計を自然言語ベースで作成（各ページ内の表示と操作の設計、データベース設計、CRUD設計、API設計、認証認可設計）します。この段階でほぼAIが自然言語をプログラミング言語に翻訳するだけで完成することを目指してはいます。設計の結果は/design/designsに保存してあります。
2. それを元として、AIが1機能の作成工程をサブステップに分解し、サブステップごとにコード案を提案します。人間側がそれを承認/提案することでコードが確定します。
3. これを繰り返します。途中で判断が必要になった場合はその都度設計を書き直して、反映させ、その新しい設計通りにコードを作成します。

2週間以内にどこまでできるか、という実験的なプロジェクトです。

> 設計（Phase 0〜4）と、実装の土台づくり（Phase 5）が完了しました。Docker で起動でき、企業・学生のアカウントでログインしてホームに入り、ログアウトするまでが動きます。

## このプロダクトの考え方

### コンセプト

- エンジニア職の**長期インターンに特化**した、募集・スカウトサービス
- スキルがまだ未熟な学生でも、熱意と考え方で企業と出会える場をつくる
- お金を払うのは企業なので、**企業の課題を中心に**機能を考える。ただし学生側にも使う理由を用意する

### 企業は学生をどう探しているか

企業は学生を、次の2種類の情報で探していると考えました。

| 種類 | 例 |
| --- | --- |
| 断言できる情報 | 今のスキル、働ける期間、稼働時間（ただし自己申告） |
| 憶測でしか語れない情報 | 社風に合うか、業務やプロダクトに興味があるか、就職先の候補として見てくれるか、成長の見込み、申告どおり続けてくれるか |

**後者の推測の精度を上げること**が、マッチングの質を上げることにつながる。これがこのプロダクトの役割です。

### 設計の方針

- **推測の材料は「学生が得をする入力」で集める。** 性格の回答や稼働条件など、学生が自分のために入力するものが、そのまま企業の判断材料になるようにする
- **点数ではなく根拠を見せる。** 「一致度82%」ではなく、稼働条件の項目ごとの一致や、カルチャー5軸のずれを見せる。おすすめの計算に数値は使うが、合計点は画面に出さない
- **公正さに配慮する。** 大学名・学部・住んでいる都道府県は、おすすめの計算に使わない。性格・カルチャーは検索の絞り込みには使わない。見送り・不合格は、おすすめの計算に一切使わない

## 作る機能・作らない機能

サービスの範囲は「募集の掲載 → スカウト・応募 → マッチ → メッセージ開始」までです。面談日程の調整から先は、企業側の手段（外部のフォームやメール）に任せます。

### 作る機能（19画面：企業側10・学生側9）

| 分類 | 機能 | 主な画面 |
| --- | --- | --- |
| アカウント | 企業・学生の新規登録（ステップ形式）、ログイン・ログアウト | 新規登録、ログイン |
| プロフィール | 企業プロフィール・学生プロフィールの編集、アイコン画像 | 企業プロフィール編集、マイページ |
| 募集 | 募集の作成・編集、状態（非公開／掲載中／終了）の切り替え | 募集一覧（企業）、募集詳細編集 |
| 探す | 学生による募集の検索、企業による学生の検索、企業詳細の閲覧 | 募集一覧（学生）、学生検索、企業詳細 |
| スカウト・応募・マッチ | スカウトの送信、応募、マッチ、見送り・合格・不合格、候補者の整理 | 学生詳細、募集詳細、候補者一覧、募集管理、スカウト管理 |
| メッセージ | 企業×学生の1スレッドでの送受信（マッチが1つもない間は送れない） | メッセージ管理 |
| おすすめ | 募集一覧のおすすめ順、「○○募集におすすめ順」の学生検索、似た学生・似た募集のポップアップ | 募集一覧（学生）、学生検索、学生詳細、募集詳細 |
| 通知（企業向けのみ） | 他社で見送られた学生を「おすすめの学生」として知らせる | 通知 |
| 比較の表示 | 稼働条件・職種・技術・業界の一致と、カルチャー5軸のずれ | 学生詳細、募集詳細 |

課題の必須要件との対応は次のとおりです。

| 課題の要件 | 対応する機能 |
| --- | --- |
| インターン生が登録できる | 学生の新規登録・プロフィール編集 |
| 企業がインターン生にメッセージを送れる | スカウトの送信、メッセージ管理 |
| 企業が募集を掲載できる | 募集の作成・編集・掲載 |
| （追加機能の例）インターン生の検索機能 | 学生検索（おすすめ順・推薦検索つき） |

### 作らない機能（主なもの）

- 学生向けの通知
- お気に入り、特定企業のブロック、口コミ
- パスワードの再設定、メールアドレスの確認（メール送信が必要になるため今回は後回し）
- メッセージ・通知のリアルタイム更新（画面を開いたとき・再読み込みしたときに最新を取る。リアルタイム性はそこまで求めていないと判断）
- 運営（管理者）の画面
- 1社に複数の担当者（1社1アカウント）

## 説明したい設計判断

| 判断 | 理由 |
| --- | --- |
| 応募とスカウトを「やりとり」1つのテーブルにまとめる | 「募集×学生」で1件として扱えば、どちらから始まっても同じ流れで管理でき、候補者管理とメッセージを分けずに済む |
| やりとりの「発生元（応募／スカウト）」と「状態」を別の列で持つ | 状態に発生元を含めると、「発生元は応募なのに状態はスカウト待ち」のような矛盾したデータが作れてしまう |
| マッチは「後から意思表示した側」が成立させる | 双方が合意して初めて会話が開くので、学生は1つの募集について、マッチするまで連続したメッセージを受けない |
| 稼働条件を学生と企業で同じ物差しにする | 「学生の上限 ≥ 企業の下限」という単純な比較だけで、照合と推薦検索ができる |
| 見送り・不合格は関係を断たず、企業の一覧から隠すだけ | 企業が「一覧を片付けたい」という動機で状態を付けることが、そのまま採用の転換率のデータになる |
| 検索の条件で結果を減らさず、合う相手を上・合わない相手を下に並べる | 条件を書いていない募集も埋もれない。「掲載中の募集をすべての学生が見られる」前提も崩れない |
| おすすめは「内容の近さ」と「行動の近さ」を組み合わせる | 行動データが少ないうちは内容を重視し、増えるほど行動を重視する。文章のエンベディングは使わない |
| おすすめの更新は、裏側のジョブで毎回元データから計算し直す | 失敗して再実行しても値がずれない。推薦の計算が失敗しても、応募そのものは失敗しない |
| 性格・カルチャーの軸は既存の研究を参考にする | 相性研究（リクルートの相性5軸、ホフステードの組織文化の6次元）を参考に、どちらを選んでも良さそうな軸にした |

## 技術構成

| 分類 | 使うもの | 選んだ理由・補足 |
| --- | --- | --- |
| バックエンド | Rails 8（API モード） | 課題の指定。画面は作らず API だけを担当する |
| フロントエンド | Next.js | 課題の指定。画面はすべてこちらで作る |
| 画面の部品 | Tailwind CSS ＋ shadcn/ui | 部品のソースを手元にコピーする方式の部品集。色を変数で管理し、後から見た目を1か所で整えられるようにしている |
| データベース | PostgreSQL | 配列型・JSON 型が使える。Rails で広く使われている |
| ログイン方式 | Cookie ＋ セッション（Rails 8 標準の認証ジェネレーター） | HttpOnly を付け、Secure は本番のみ有効。パスワードは has_secure_password で保存 |
| 画像 | Active Storage | 企業・学生のアイコン |
| 裏側の処理 | Active Job ＋ Solid Queue | 推薦テーブルの更新と通知の作成 |
| 動かし方 | Docker | 手元で起動できることを完成の条件とする。クラウドへの公開は任意 |

### 通信の経路

```
ブラウザ → Next.js（3000番）→ rewrites で転送 → Rails（3001番）
```

- ブラウザから見ると同じオリジンになるので、CORS の設定が要りません
- ログイン後の画面では、データの取得・送信をすべてブラウザ側から、この経路で行います
- Rails を API モードで作るとセッションと CSRF 対策が無効になるため、有効に戻して使います

### 品質の方針

- **守り（権限の確認）は Rails に置く。** 画面側の振り分けは見た目のためだけ
- **判定は Rails で計算して返す。** やりとりの状態、押せるボタン、稼働条件の一致などを、画面側では計算しない（同じ判定を2つの言語で書かないため）
- **番号はその人が見てよい範囲の中から探す。** 範囲外の番号は 404 を返す
- テストは Rails の API テストが中心。権限の確認と、主要な流れ（登録 → 募集 → スカウト → メッセージ）を1本通す
- 重さ対策として、N+1 問題の回避、外部キーへのインデックス、一覧のページ分けを行う

## 動かし方

### 必要なもの

- Docker Desktop
- bash（Mac・Linux は標準のもの。Windows は Git に付いてくる Git Bash）

### 起動する

リポジトリのルートで、次の1行を実行します。

```bash
bash dev.sh setup
```

`setup` は、次の4つを順に行います。何度実行してもかまいません（すでにあるものは作り直しません）。

1. `code/.env` がなければ、見本の `code/.env.example` から作る
2. コンテナ（データベース・Rails・Next.js）を作る。初回は部品のインストールで数分かかります
3. データベースを作り、テーブルと試しのアカウントを入れる
4. 起動する

起動したら、ブラウザで http://localhost:3000 を開きます。学生のログイン画面が出ます。開発用の起動なので、各画面を初めて開いたときは十数秒かかります。

試しのアカウント

| 種別 | メールアドレス | パスワード |
| --- | --- | --- |
| 企業 | company@example.com | password |
| 学生 | student@example.com | password |

画面をいろいろなデータで試したいときは、仮のデータ（企業5社・募集20件・学生20人と、応募・スカウト・メッセージ）を入れられます。何度実行してもかまいません（前回の仮のデータを消して作り直します。上の試しのアカウントや、画面から登録したアカウントは消しません）。

```bash
bash dev.sh demo
```

| 種別 | メールアドレス | パスワード |
| --- | --- | --- |
| 企業 | demo-company1@example.com 〜 demo-company5@example.com | password |
| 学生 | demo-student1@example.com 〜 demo-student20@example.com | password |

### そのほかのコマンド

| コマンド | 中身 |
| --- | --- |
| `bash dev.sh start` | 起動する |
| `bash dev.sh stop` | 止める（データは残る） |
| `bash dev.sh reset` | コンテナとデータをすべて消して、最初から作り直す（確認あり） |
| `bash dev.sh test` | Rails のテストを実行する |
| `bash dev.sh lint` | 画面側（Next.js）の型のチェックと、コードの点検をする |

### Windows で動かすときの注意

- **Git Bash で実行してください。** PowerShell で `bash` と打つと WSL の bash が動き、Docker を使えないことがあります。VS Code なら、ターミナルの種類で「Git Bash」を選べます
- リポジトリを Windows 側（`C:\…`）に置いて動かすための工夫（画面の自動更新など）は、[開発環境.md](design/designs/開発環境.md) の 18-2・18-5 にあります

秘密の情報（`.env`、`config/master.key`）はリポジトリに入れていません。必要な項目は `code/.env.example` で示しています。

## 今回のスコープ外と、本番運用で必要になること

プロトタイプとして割り切った点です。本番で運用する場合は、次の対応が必要になります。

| 項目 | 今回の扱い | 本番運用で必要になること |
| --- | --- | --- |
| 掲載審査 | 運用で行う前提とし、今回はスコープ外 | 運営の画面と審査の流れ |
| やりとりの状態の変更履歴 | 残さない | 返信率や転換率を期間ごとに出すには、履歴のテーブルを追加する |
| 退会・データ削除 | スコープ外 | 個人情報の削除依頼への対応として、論理削除（削除フラグを立てて見えなくする）など |
| メールアドレス・パスワードの変更 | スコープ外 | プロフィールとは別の「アカウント設定」の窓口 |
| データの誤削除 | 外部キーは既定の動き（参照されている行は消せない）のままなので、誤って消えることはない | ― |
| 法令の確認 | おすすめ順・通知は「掲載中の募集をすべての学生が、活動中の学生をすべての企業が見られる」前提を崩さない形にしており、職業安定法の「選別」「加工」には当たらないと読んでいる（専門家の判断ではない） | 運用前に、労働局や専門家への確認 |

## 開発の進め方

- AI（Claude Code）と相談しながら、設計 → 実装の順に進めています
- AI からの提案・反論には `PR1`、`PR2` … と通し番号を付け、開発者が番号ごとに承認か反論をします。触れなかった番号は「未決」とし、設計書にもコードにも入れません
- 決まったことは `design/designs/` に反映し、話し合いの「決めたこと」と「決めなかったこと」を `minutes/` の議事録に残します
- 実装中に設計との食い違いが見つかったら、コードだけを合わせず、どちらを直すかを決めてから進めます
