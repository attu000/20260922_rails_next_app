## 17. 権限とバリデーション（Phase 4-2・4-3）

- HTTP ステータスと、エラーを返すときの共通の形は本書16-1-10
- ログインの確認と、種別ごとの入口の分け方は本書16-1-3・16-1-6

### 17-1. 権限表（Phase 4-2）

- 未着手。進め方は本書11-1
- 誰が何をできて、何をできないかを、窓口（本書16-3）ごとにまとめる
- 決まっていること：入口ごとの種別の確認（本書16-1-3）、番号の探し方（見てよい範囲。本書16-1-10）
- 一緒に決める未決：企業プロフィールが未入力の状態で、募集の作成やスカウトを許すか（本書10-2）

### 17-2. 状態遷移表（Phase 4-2）

- 未着手。進め方は本書11-1
- 対象
  - やりとり：発生元 × 状態 × 募集の状態 × 誰が押すか（今の定めは本書5-1、本書6-5 C6 の「操作（その募集での状態ごと）」）
  - 募集の状態（本書5-3）
  - メッセージを送れるかどうか（本書5-2）
- 状態を変える操作は、操作ごとに専用の URL にする（本書16-1-4）ので、この表の1行が窓口1本に対応する
- 案：本書16-3-6 の「状態を変える操作」の表（できる状態）。画面に出すボタンは、この表の判定を API が返す（本書16-3-2 形D の available_actions）
- 募集の状態は、募集の保存で一緒に変える（本書16-1-4 の例外）。新規作成のときは下書きか掲載中だけ、一度掲載したら下書きに戻せない

### 17-3. エラーとバリデーション（Phase 4-3）

#### 17-3-1. ログイン・新規登録のエラー

- ログインに失敗したとき（C8・S8）
  - 「ログインができません」とだけ表示する（HTTP ステータスは 401）
  - メールアドレスとパスワードのどちらが違うか、メールアドレスが登録済みかどうかは出さない
- 新規登録（C9・S9）
  - 項目ごとに理由を表示する（HTTP ステータスは 422）
  - メールアドレスが登録済みのときも、その項目に「登録済み」とはっきり表示する。ステップ1から進むときの重複確認でも、最後の「登録する」でも同じ
  - 入力の誤り（パスワードが短い、確認用と一致しない、など）も、項目ごとに理由を表示する
  - 登録済みかどうかが第三者に分かってしまう点（アカウント列挙）は、プロトタイプでは対策しない

#### 17-3-2. その他（未着手）

- 未着手。進め方は本書11-1
- 入力にするもの：必須項目（本書5-9）、パスワードのルール（本書5-11）、応募理由の最低1つ必須、登録ステップの検証
- 画面側と Rails 側の検証の分担、エラー文言
- スカウト文・メッセージの本文の長さの上限（本書16-3 ㉔・㊳・㊶）
- 新規登録のステップ1の他の項目（パスワードの長さなど）を、メールアドレスの確認（本書16-3 ④）でも確かめるか
- 一緒に決める未決：登録ステップ（C9・S9）で各項目を必須にするか、「あとで入力する」で飛ばせるようにするか（本書10-2）
