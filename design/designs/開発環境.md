## 18. 開発環境（Phase 5〜）

- 手元で動かすための環境（Docker の構成、バージョン、ひな形の作り方、部品の固定や不具合の回避策、開発用のコマンド）を書く
- 設計の判断（何を・なぜ作るか）は本書3章。ここは「どう動かすか」で、部品を足すたびに変わる
- ほかの章と同じく、今の状態だけを書き、古い内容は置き換える。回避策には「いつ外すか」を必ず書く

### 18-1. Docker の構成

- Docker で手元起動できれば「完成」とする（本書3-1 A-4）
- `code/docker-compose.yml` に3つのコンテナを書く。まとまりの名前（`name:`）は `rails_next_test`

| コンテナ | 中身 | ポート | 補足 |
| --- | --- | --- | --- |
| db | PostgreSQL | 外に開けない | つなぐのは同じ Docker の中の Rails だけのため。データはボリューム `postgres_data` に置く。ヘルスチェック（受け付けられる状態かの確認）を5秒ごとに行う |
| backend | Rails（API 専用） | `127.0.0.1:3001` | `code/backend/Dockerfile.dev` で作る。入れた部品（gem）はボリューム `bundle_data` に、アップロードされたファイル（アイコン。Active Storage の `storage/`）はボリューム `storage_data` に置く（本書9-3）。db が準備完了（healthy）になってから起動する |
| frontend | Next.js | `127.0.0.1:3000` | `code/frontend/Dockerfile.dev` で作る。`node_modules` と `.next` はボリュームに置く。転送先の Rails の住所を `RAILS_API_URL=http://backend:3001` で渡す |

- ポートに `127.0.0.1` を付けて、このパソコンからだけつながるようにする
- パスワードなどは `code/.env` に書き、Git には項目の見本の `code/.env.example` だけを入れる
- 開発では、開発用の `Dockerfile.dev` を使う。Rails の本番用の `Dockerfile`（`rails new` が作ったもの）はそのまま残す
- Rails の接続先のデータベースは、`config/database.yml` が環境変数（`DB_HOST`・`DB_USERNAME`・`DB_PASSWORD`）から読む。値は compose が渡す
- Next.js から Rails への転送の細部（Phase 5 のステップ3・4 で確かめた）
  - Next.js は、転送先を `backend:3001` に書き換え、元の住所（`localhost:3000`）を `X-Forwarded-Host` に入れて渡す
  - Rails の開発用の設定で、`backend` あての接続を受け付ける（`config.hosts << "backend"`。Django の `ALLOWED_HOSTS` にあたる）
  - Rails は `X-Forwarded-Host` を使うので、CSRF 対策の「送り元と宛先が同じか」の確認（Origin の確認）は、追加の設定なしで通る

### 18-2. ファイルを置く場所

- Windows 側（`C:\Users\…`）のまま進める
- Docker（Linux）から Windows 側のファイルを読むと、変更の知らせが届かず、遅れやすい。次の対策を入れている
  - 画面の自動更新はポーリング（定期的に見に行く方法）で行う（本書18-5）
  - `node_modules` などの大きなフォルダは、Docker のボリュームに置く
- 手元の `code/frontend/node_modules`（ひな形を作ったときにできたもの）は消さない。コンテナは使わないが、AGENTS.md が指す Next.js の説明書（`node_modules/next/dist/docs/`）と、VS Code の型のチェックがこれを使うため。Git には入らない
- 遅さや負荷が気になったら、リポジトリを WSL2（ダブリューエスエル・ツー）側に移す。Next.js の公式の説明書がすすめる方法。移したら、本書18-5 の画面の自動更新の回避策を外す

### 18-4. ひな形の作り方

- どちらも Docker の使い捨てのコンテナの中で作る。Windows で直接作ると、Windows 用の設定がファイルに混ざり、Docker（Linux）で動かなくなることがあるため。手元の Ruby・Node.js は使わない
- Rails：API モード（`--api`）、データベースは PostgreSQL。基本は標準のままにし、使わないと決まっているものだけ外す
  - 外すもの：Action Cable（アクションケーブル。リアルタイム通信。リアルタイム更新は作らないため。本書4-3）、Kamal（ケイマル。本番公開の道具。クラウドへの公開は任意のため）、CI（シーアイ。GitHub で自動テストを動かす設定の `.github/`。GitHub はリポジトリのルートの `.github/` しか読まず、`code/backend/` の中では動かないため。必要になったら Phase 8 でルートに作る）
  - 残すもの：Solid Queue（推薦のジョブで使う）、RuboCop（ルボコップ。コードの書き方の点検）、Brakeman（ブレークマン。セキュリティの点検）
  - 作ったあと、`code/backend/` の中にできる Git の管理フォルダ（`.git`）を消す。リポジトリはルートで Git 管理しているため
- Next.js：TypeScript（タイプスクリプト）、App Router（アップルーター）、`src/` フォルダは使わない（本書16-1-6 の `app/page.tsx` の形）、見た目は Tailwind CSS（テイルウィンド・シーエスエス）と shadcn/ui（下の項目）、コードの点検は ESLint（イーエスリント）、パッケージ管理は npm
  - React Compiler（リアクト・コンパイラー。画面の描き直しを自動で減らす仕組み）は使わない。Next.js がおすすめする標準の組み合わせに入っておらず、後からでも有効にできるため
  - AGENTS.md（エージェンツ・エムディー）を入れる。AI に、手元に入っている Next.js 自身の説明書を読んで最新の書き方を確かめさせるファイル。AI の知識が Next.js 16 より古いことによる誤りを防ぐため
  - `create-next-app` の `--disable-git` で、`code/frontend/` の中に Git を作らない
- shadcn/ui（本書3-1 A-8）：起動中の frontend のコンテナの中で、バージョンを指定して実行する（`code/` で `docker compose exec frontend npx shadcn@4.21.0 …`）
  - 導入：`init --defaults`。`--template=next --preset=base-nova`（Next.js、Base UI、標準の見た目）と同じ意味で、質問に答えずに導入できる。Git Bash では対話式の質問がうまく出ないことがあるため、この形にした
  - 設定（`components.json`）：色の系統（`baseColor`）は `neutral`、色を変数で管理する（`cssVariables`）は `true`。**この2つは導入した後から変えられない**
  - 部品の追加：`add button input label` のように名前を指定する。`components/ui/` に置かれる。使うときに1つずつ足す
  - 導入のときの修正：`init` は「書体の更新」と表示したが `app/layout.tsx` を書き換えず、`app/globals.css` の `--font-sans` が自分自身を指したままになっていた（書体が決まらない）。`app/layout.tsx` の Geist の `variable` を `--font-sans` にして直した。Geist には日本語の文字がないので、日本語は OS の書体で出る
  - 画面の色は、OS のダークモードに合わせて自動で黒くならない。`dark` という印を付けたときだけ黒くなる形なので、今は常に白い画面

### 18-5. 部品の固定と、不具合の回避策

| 問題 | 回避策 | 外す条件 |
| --- | --- | --- |
| json 3.0 では、Rails 8.1.3.1 が Cookie（セッション）を読む処理が失敗し、Cookie を送り返すリクエストがすべて 500 になる（Phase 5 のステップ4 で確かめた。Rails の課題 #58784） | Gemfile で `gem "json", "< 3"` として 2 系に固定する | Rails 側の修正（#58601。8.1 系の開発版に取り込み済み）を含む版が出たら、Rails を上げて固定を外す |
| Windows 側のファイルを Docker で読むと、変更の知らせが届かず、保存しても画面が自動で更新されない（Phase 5 のステップ3 で確かめた） | 開発のときだけ webpack（ウェブパック）に切り替え、ポーリングを入れる。compose の frontend で、起動を `npm run dev -- --webpack` にし、`WATCHPACK_POLLING: 1000`（1秒ごとに確かめる）を書く。webpack と Next.js 自身のファイルの見張り役の両方がこの値を読む | リポジトリを WSL2 側に移したら、`--webpack` と `WATCHPACK_POLLING` を消す |

画面の自動更新の補足

- Turbopack（ターボパック。Next.js 16 の標準の道具）のままポーリングを入れる方法（`next.config.ts` の `watchOptions.pollIntervalMs`）は、設定は届いていたのに変更に気づかなかったため採らない
- 開発（webpack）と本番の組み立て（Turbopack）で道具が変わる。Phase 8 で本番の組み立て（`next build`）を一度動かして、違いが出ないか確かめる
- Next.js の公式の説明書は、ポーリングを「最後の手段」としている（反映の遅れとパソコンの負荷）。Phase 5 のステップ3 の時点で、CPU の使用率は 1〜2% で問題なかった
- 開発中の Next.js は、各画面を初めて開いたときにその画面だけを組み立てるので、初回は十数秒かかる（2回目からは 0.2秒ほど）。webpack と、Windows 側のファイルの読み込みが重なっているため。本番（`next build`）では事前に組み立てるので起きない

### 18-6. 開発用のコマンド（`dev.sh`）

- 起動などの操作を、リポジトリのルートの `dev.sh` にまとめている。`bash dev.sh <コマンド>` で実行する
  - `bash dev.sh …` の形にしているのは、ファイルの実行の権限がなくても動き、Windows・Mac・Linux で同じ打ち方になるため
- Windows では Git Bash で実行する。PowerShell で `bash` と打つと WSL の bash が動き、Docker を使えないことがある
- どこから実行しても `code/` に移ってから動く。Git Bash が「/ で始まる引数」を Windows のパスに書き換えないよう、`MSYS_NO_PATHCONV=1` を設定している

| コマンド | 中身 |
| --- | --- |
| `setup` | `code/.env` がなければ見本から作る → コンテナを作る → データベースを作り、テーブルと試しのアカウントを入れる（`db:create db:migrate db:seed`）→ 起動する。何度実行してもよい |
| `start` | 起動する |
| `stop` | 止める（データは残る） |
| `reset` | コンテナとボリューム（データベースの中身、部品の置き場所）をすべて消して、`setup` からやり直す。確認あり |
| `test` | Rails のテスト（RSpec）を実行する |
| `lint` | Next.js の型のチェック（`tsc --noEmit`）と、コードの点検（ESLint）をする |
| `logs` | ログを出し続ける。コンテナを指定できる |
| `help` | コマンドの一覧を出す |

- 試しのアカウント（`db/seeds.rb`）：企業 `company@example.com`、学生 `student@example.com`。パスワードはどちらも `password`。開発用なので単純にしている
