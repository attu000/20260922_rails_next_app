## 3. 技術構成と品質の方針（Phase 0）

### 3-1. 技術構成

- A-1 ログイン方式：Cookie（クッキー）＋セッション。HttpOnly（エイチティーティーピーオンリー）付き、Secure（セキュア）は本番のみ有効。Django と同じ考え方が使える
- A-2 Rails と Next.js の役割分担：Rails は API 専用、画面はすべて Next.js。ブラウザからは Next.js の rewrites（リライト）で Rails に転送する。同一オリジンになるので CORS（コルス）の設定が不要
  - 経路：ブラウザ → Next.js（3000番）→ rewrites で転送 → Rails（3001番）
  - ログイン後の画面では、データの取得・送信をすべてブラウザ側から、この経路で行う。Next.js のサーバー側から Rails を呼ばない（本書16-1-1）
  - 注意点1：Rails を API モードで作るとセッションが無効になるため、Cookie とセッションのミドルウェアを有効に戻す
  - 注意点2：CSRF（シーエスアールエフ、なりすまし送信）対策を入れる。Rails がトークンを発行し、フロントが送り返す。受け渡しの方法は本書16-1-7
  - 注意点3：ブラウザからの通信に credentials（クレデンシャルズ）の指定を付ける
  - 注意点4：Docker（ドッカー）上では転送先がコンテナ名になるので、環境変数で切り替えられるようにする
  - 注意点5：アイコン画像の URL（`/rails/active_storage/...`）も rewrites の転送対象に含める（本書9-3）
- A-3 データベース：PostgreSQL（ポストグレスキューエル）。配列型・JSON（ジェイソン）型が使える。Rails の事実上の標準
- A-4 動かし方：Docker で手元起動できれば「完成」とする。クラウド公開は最終日の任意項目
  - 構成：`code/docker-compose.yml` に、データベース（db）・Rails・Next.js のコンテナを書く。まとまりの名前（`name:`）は `rails_next_test`
  - データベースのコンテナはポートを外に開けない。つなぐのは同じ Docker の中の Rails だけのため
  - パスワードなどは `code/.env` に書き、Git には項目の見本の `code/.env.example` だけを入れる
  - ファイルを置く場所：Windows 側（`C:\Users\…`）のまま進める。Docker（Linux）から Windows 側のファイルを読むと、変更の検知が遅れやすいので、次の対策を入れる。それでも遅ければ、WSL2（ダブリューエスエル・ツー）側へ移すことを考える
    - Next.js の変更の検知を、定期的な確認（ポーリング）に切り替える（下の A-7）
    - `node_modules` などの大きなフォルダは、Docker のボリュームに置く
  - ひな形（`rails new`、`create-next-app`）も Docker のコンテナの中で作る。Windows で直接作ると、Windows 用の設定がファイルに混ざり、Docker（Linux）で動かなくなることがあるため。手元の Ruby・Node.js は使わない
- A-5 リポジトリ構成：モノレポ（1つのリポジトリに、設計書とコードの両方を入れる）。提出が1つの URL で済み、設計から実装までが1本のコミット履歴としてつながる
  - ルート直下：`README.md`（提出物の説明）、`CLAUDE.md`（実装フェーズの指示書）、`.gitignore`
  - `minutes/`：議事録。設計と実装の両方の話し合いを記録するので、`design/` や `code/` の中ではなくルートに置く
  - `design/`：設計書（designs/）、出発点の資料（premise/。Git 管理外）
  - `code/`：`backend/`（Rails）、`frontend/`（Next.js）、`docker-compose.yml`
  - ブランチ運用：開発者が行う（本書9-7）
- A-6 バージョン：作業するときの最新の安定版を使う。長期サポート版（LTS）があるものは LTS にする。確かめたバージョンは下の表に書く

- A-7 ひな形の作り方
  - Rails：API モード（`--api`）、データベースは PostgreSQL。基本は標準のままにし、使わないと決まっているものだけ外す
    - 外すもの：Action Cable（アクションケーブル。リアルタイム通信。リアルタイム更新は作らないため。本書4-3）、Kamal（ケイマル。本番公開の道具。クラウドへの公開は任意のため）、CI（シーアイ。GitHub で自動テストを動かす設定の `.github/`。GitHub はリポジトリのルートの `.github/` しか読まず、`code/backend/` の中では動かないため。必要になったら Phase 8 でルートに作る）
    - 作ったあと、`code/backend/` の中にできる Git の管理フォルダ（`.git`）を消す。リポジトリはルートで Git 管理しているため
    - 開発では、本番用の `Dockerfile` ではなく、開発用の `Dockerfile.dev` を使う。本番用はそのまま残す
    - 残すもの：Solid Queue（推薦のジョブで使う）、RuboCop（ルボコップ。コードの書き方の点検）、Brakeman（ブレークマン。セキュリティの点検）
  - Next.js：TypeScript（タイプスクリプト）、App Router（アップルーター）、`src/` フォルダは使わない（本書16-1-6 の `app/page.tsx` の形）、見た目は Tailwind CSS（テイルウィンド・シーエスエス）、コードの点検は ESLint（イーエスリント）、パッケージ管理は npm
    - React Compiler（リアクト・コンパイラー。画面の描き直しを自動で減らす仕組み）は使わない。Next.js がおすすめする標準の組み合わせに入っておらず、後からでも有効にできるため
    - AGENTS.md（エージェンツ・エムディー）を入れる。AI に、手元に入っている Next.js 自身の説明書を読んで最新の書き方を確かめさせるファイル。AI の知識が Next.js 16 より古いことによる誤りを防ぐため
    - `create-next-app` の `--disable-git` で、`code/frontend/` の中に Git を作らない
    - 画面の自動更新：Windows 側のファイルを Docker で読むと、変更の知らせが届かず、保存しても画面が自動で更新されない（Phase 5 のステップ3 で確かめた）。開発のときだけ webpack（ウェブパック）に切り替え、ポーリング（定期的に見に行く方法）を入れて対処する
      - `code/docker-compose.yml` の frontend で、起動を `npm run dev -- --webpack` にし、`WATCHPACK_POLLING: 1000`（1秒ごとに確かめる）を書く。webpack と Next.js 自身のファイルの見張り役の両方がこの値を読む
      - Turbopack（ターボパック。Next.js 16 の標準の道具）のままポーリングを入れる方法（`next.config.ts` の `watchOptions.pollIntervalMs`）は、設定は届いていたのに変更に気づかなかったため採らない
      - 開発（webpack）と本番の組み立て（Turbopack）で道具が変わる。Phase 8 で本番の組み立て（`next build`）を一度動かして、違いが出ないか確かめる
      - Next.js の公式の説明書は、ポーリングを「最後の手段」としている（反映の遅れとパソコンの負荷）。遅さや負荷が気になったら、リポジトリを WSL2 側に移す（公式のおすすめ）。そのときは compose の `--webpack` と `WATCHPACK_POLLING` を消す
- 使う Rails 8 の標準機能
  - 認証：Rails 8 標準の認証ジェネレーター（コードの自動生成機能）。ログイン中のセッションを sessions テーブルで持つ
    - ジェネレーターはメールアドレスの列を `email_address` という名前で作るが、設計書のとおり `email` に直す（API のキー名もすべて `email` のため。本書8-5）
    - パスワード再設定の部品も一緒に作られるが、作らないので外す（本書4-3）。ログインの回数制限（3分間に10回）は最初から入っているので、そのまま使う（本書16-3 ①）
  - パスワード：has_secure_password（ハズ・セキュア・パスワード）で暗号化して保存する
  - 画像：Active Storage（アクティブストレージ）。企業・学生のアイコンに使う
  - 裏側の処理（ジョブ）：Active Job（アクティブジョブ）と Solid Queue（ソリッドキュー）。推薦テーブルの更新と通知の作成に使う

### 3-2. データの考え方

- B-1 応募とスカウト：「やりとり」1テーブルに統合する。「企業-学生」ではなく「募集-学生」で1件。発生元（応募／スカウト）と状態を別の列で持つ
- B-2 チャットの紐づけ：「企業×学生」で1スレッド（募集ごとには分けない）
- B-3 アカウント構造：ログイン情報（メール、パスワード、種別）と、プロフィール（学生／企業）を別テーブルに分ける
- B-4 運営（管理者）：作らない。掲載審査は README で「運用前提・今回はスコープ外」と明記する

### 3-3. 品質の方針

- D-1 テスト：Rails の API（リクエスト）テスト中心。権限の確認と、主要な流れ（登録 → 募集 → スカウト → メッセージ）を1本。推薦の計算は、単体でテストできる部品にまとめる（本書9-4）
  - 道具：RSpec（アールスペック）と、テストデータを作る FactoryBot（ファクトリーボット）。日本の Rails の現場で最も多く使われていて、API のテストを request spec の形でそのまま書けるため
  - 必ず入れるもの：ログイン画面を初めて開いた人が、そのままログインできること（本書16-1-7）。他社の番号や、見てよい範囲の外の番号が 404 になること（本書16-1-10）
- D-2 セキュリティ：自分で設計するのは権限制御と個人情報の出し分け。パスワード保存・SQL（エスキューエル）インジェクション対策・パラメータ制限はフレームワーク標準に乗る。ログインの回数制限は Rails 標準機能で入れられれば入れる
- D-3 重さ対策：N+1問題（エヌプラスワン）の回避、外部キーへのインデックス、一覧のページ分け

## 9. 設計・実装のルール（Phase 5 以降で守ること）

### 9-1. 後で変えると大変なものへの対策

- enum は番号を明示して書き、新しい値は末尾に足す
  - 理由：並び順の番号で保存される書き方だと、途中に差し込んだときに既存データの意味がずれる
- マスタは code か name で管理し、削除しない
  - 理由：募集・学生・（Phase 7 の）体験がすべて参照するため、統合・分割すると全データの付け替えが必要になる
  - 非表示が必要になったら、表示するかどうかの列を後から足す
- 「今の会社」を取り出す処理を1か所（ヘルパー（共通の関数））にまとめ、各所で `current_user.company_profile` を直接書かない
  - 理由：将来、1社に複数の担当者を持たせるときに、修正を1か所で済ませるため
  - メッセージの送信者はすでにユーザー単位なので、そのまま使える
- 性格・カルチャーの軸の定義（列名、両端の説明）をコードの1か所にまとめ、比較処理は「軸の一覧を順に比べる」形で書く
- 稼働条件の選択肢（1／3／6／9／12 など）と検証を、共通のモジュール（Rails の concern（コンサーン））1か所にまとめる
- 推薦のパラメータは、データベースではなく、コードの設定ファイル1か所にまとめる（本書7-4）

### 9-2. 処理の決まりごと

- スカウト送信時は、次の4つを1つのトランザクション（まとめて成功か、まとめて取り消しにする処理）で作る
  - やりとり（candidacies）
  - スレッド（まだなければ message_threads）
  - メッセージ（messages）
  - スカウトメッセージ（scout_messages）
- 応募がマッチしたときは、やりとりの更新と、スレッドの作成（まだなければ）を1つのトランザクションで行う
- 新規登録（C9・S9）は、最後の「登録する」で、アカウント・プロフィール・付属情報を1つのトランザクションでまとめて作る。アイコンは登録の直後に別の窓口で送る（本書16-3 ⑤）
- 応募・スカウトへのマッチでは、candidacies、candidacy_reasons、reason_mask を同じトランザクションで保存する
- 推薦テーブルの更新と通知の作成は、元の処理のトランザクションが確定した後に、裏側のジョブとして実行する。推薦用のジョブは専用の待ち行列に入れ、1つずつ順番に実行する（本書7-5）
- チャット画面では、Message に `has_one :scout_message`（ハズワン）を付け、スカウトかどうか・どの募集のものかをまとめて読み込む（N+1問題を避ける）
- 学生詳細（C6）では、自社の全募集ぶんの比較を一度に返すので、募集の職種・工程・技術・企業の業種をまとめて読み込む（本書16-3 ㉓）。Phase 8 の重さの点検の対象にする

### 9-3. アイコン（Active Storage）の実装メモ

- 送り方
  - アイコンだけは、JSON ではなく multipart/form-data で、専用の窓口に送る（本書16-3 ⑩・⑰）
- 形式とサイズの制限
  - PNG・JPEG・WebP だけを受け付け、2MB 程度を上限にする
  - Rails には添付ファイルの検証が標準で入っていないため、モデルに自分で検証を書く
- 一覧での N+1問題
  - 一覧画面では `with_attached_icon` を付けて、アイコンをまとめて読み込む
- Next.js からの転送
  - 画像の URL は `/rails/active_storage/...` という形になる
  - Next.js の rewrites の転送対象に、このパスも含める
- 保存先
  - 手元の Docker 環境では、サーバーのディスクに保存される
  - コンテナを作り直しても消えないよう、保存フォルダ（storage/）を Docker のボリュームに割り当てる
- 画像の縮小
  - 縮小版を作るには、画像処理のライブラリ（libvips（リブヴィップス））を Docker のイメージに入れる必要がある
  - 最初はサイズ上限だけで進め、Phase 8 の重さの点検で必要なら追加する

### 9-4. 推薦の実装メモ

- 推薦の計算は、画面や API から切り離した1つの部品（サービスクラス）にまとめ、単体でテストできるようにする
- ダミーデータを大量に作るコマンドを用意し、処理時間を実測する（下の9-4-1）
- 全体の作り直しは、手動で実行するコマンドとして用意する（本書7-5）
- パラメータの調整（Recall@K や nDCG による評価）は後回し

#### 9-4-1. 速さの実測（Phase 6 で実装した直後と、Phase 8）

本書7-5 には**裏側のジョブ**の見積もりしかない。画面を出すときの速さは実測して確かめる。本書7-3 で条件による絞り込みをやめたため、点数を計算する候補の件数が増えていることに注意する。

**測る場面**

| --- | --- | --- | --- |
| 1 | S2 募集一覧のおすすめ順 | 画面（利用者が待つ） | 1秒以内 |
| 2 | C5 学生検索のおすすめ順 | 画面 | 1秒以内 |
| 3 | C6 スカウト後のポップアップ | 画面 | 1秒以内 |
| 4 | S6 応募完了のポップアップ | 画面 | 1秒以内 |

**1回の表示を工程に分けて測る**（1・2の場面）

| 工程 | 測るもの | 増え方の見方 |
| --- | --- | --- |
| ① 除外（SQL） | かかった時間と、残った候補の件数 | ― |
| ② 候補のデータ読み込み（職種・技術・業界・カルチャー） | 候補1件あたりのミリ秒、発行したクエリの本数 | **まとめて読まないとここで N+1 になる** |
| ③ 点数の計算（f(P, S)） | 候補1件あたりのマイクロ秒 | 候補の件数に比例するはず |
| ④ 2群への振り分けと並べ替え、20件の取り出し | ミリ秒 | 候補の件数に比例するはず |

**データ量を3段階で測る**

| 段階 | 学生 | 募集 | 1人あたりの応募 | いつ |
| --- | --- | --- | --- | --- |
| 小 | 100人 | 100件 | 3件 | Phase 6 で推薦を実装した直後 |
| 中 | 5,000人 | 1,000件 | 10件 | Phase 8 の重さの点検 |
| 大 | 100,000人 | 10,000件 | 20件 | 中までの実測から計算で外挿する（本書7-5 の運用規模の想定） |

- 小 → 中でデータが50倍になったとき、時間が**何倍になったか**を見る。50倍前後なら候補の件数に比例（想定どおり）。それよりずっと大きければ、二乗で効いている場所があるので設計を見直す
- 結果は、7-5 の見積もりの表と並べて記録する

### 9-5. README・利用規約・プライバシーポリシーに書くこと

- README
  - アピールしたい構成や工夫（本書2-6）
  - 掲載審査は運用前提・今回はスコープ外
  - やりとりの状態の変更履歴は残らない。返信率や転換率を期間ごとに出すには、運用時に履歴のテーブルを追加する

### 9-7. ブランチとコミットの運用

ブランチとコミット

- ブランチの作成・コミット・main への取り込みは、開発者が自分で判断して行う。細かい運用ルールは設けない
- AI は、指示がない限りブランチの作成やコミットをしない
- 秘密の情報（`.env`、`config/master.key`）は入れない。`.gitignore` で除外してある

改行コード

- ルートの `.gitattributes` で `* text=auto eol=lf` を指定し、**改行コードを LF にそろえる**
- 理由：Windows で編集すると行の終わりが CRLF になる。Rails の起動スクリプト（`bin/docker-entrypoint` など）が CRLF のまま Docker（Linux）に入ると、「not found」という分かりにくいエラーで止まるため
