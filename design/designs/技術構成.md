## 3. 技術構成と品質の方針（Phase 0）

### 3-1. 技術構成

- A-1 ログイン方式：Cookie（クッキー）＋セッション。HttpOnly（エイチティーティーピーオンリー）付き、Secure（セキュア）は本番のみ有効。Django と同じ考え方が使える
- A-2 Rails と Next.js の役割分担：Rails は API 専用、画面はすべて Next.js。ブラウザからは Next.js の rewrites（リライト）で Rails に転送する。同一オリジンになるので CORS（コルス）の設定が不要
  - 経路：ブラウザ → Next.js（3000番）→ rewrites で転送 → Rails（3001番）
  - ログイン後の画面では、データの取得・送信をすべてブラウザ側から、この経路で行う。Next.js のサーバー側から Rails を呼ばない（本書16-1-1）
  - 注意点1：Rails を API モードで作るとセッションが無効になるため、Cookie とセッションのミドルウェアを有効に戻す
  - 注意点2：CSRF（シーエスアールエフ、なりすまし送信）対策を入れる。Rails がトークンを発行し、フロントが送り返す。受け渡しの方法は本書16-1-7
  - 注意点3：ブラウザからの通信に credentials（クレデンシャルズ）の指定を付ける
  - 注意点4：Docker（ドッカー）上では転送先がコンテナ名になるので、環境変数で切り替えられるようにする
  - 注意点5：アイコン画像の URL（`/rails/active_storage/...`）も rewrites の転送対象に含める（本書9-3）
- A-3 データベース：PostgreSQL（ポストグレスキューエル）。配列型・JSON（ジェイソン）型が使える。Rails の事実上の標準
- A-4 動かし方：Docker で手元起動できれば「完成」とする。クラウド公開は最終日の任意項目
  - Docker の構成とファイルを置く場所は、本書18-1・18-2
- A-5 リポジトリ構成：モノレポ（1つのリポジトリに、設計書とコードの両方を入れる）。提出が1つの URL で済み、設計から実装までが1本のコミット履歴としてつながる
  - ルート直下：`README.md`（提出物の説明）、`CLAUDE.md`（実装フェーズの指示書）、`dev.sh`（開発用のコマンド。本書18-6）、`.gitignore`
  - `minutes/`：議事録。設計と実装の両方の話し合いを記録するので、`design/` や `code/` の中ではなくルートに置く
  - `design/`：設計書（designs/）、出発点の資料（premise/。Git 管理外）
  - `code/`：`backend/`（Rails）、`frontend/`（Next.js）、`docker-compose.yml`
  - ブランチ運用：開発者が行う（本書9-7）
- A-6 バージョンと部品：本書18-3
- A-7 ひな形の作り方と、部品の固定・不具合の回避策：本書18-4・18-5
- A-8 画面の見た目：Tailwind CSS の上に、部品集の shadcn/ui（シャドシーエヌ・ユーアイ）を使う
  - shadcn/ui は、ボタン・入力欄などの部品のソースコードを `components/ui/` にコピーしてくる道具。中身を読めて、直せる。Next.js と Tailwind の組み合わせで最も一般的な部品集の一つ
  - 部品の動き（キーボード操作、フォーカスなど）は Base UI（ベース・ユーアイ）に任せる。2026年7月からの shadcn/ui の標準。Radix UI（ラディックス・ユーアイ）も選べるが、公式の説明と手元のコードの形をそろえるため標準にした
  - 色・角の丸みなどは標準のプリセット（`base-nova`）のまま使う。**細かい見た目は後回し**にし、今は部品・幅・見出しの大きさを全画面でそろえるだけにする
  - 今入れた理由：後から見た目を整えるときに、`app/globals.css` の色の変数と `components/ui/` の部品を直せば全画面に効くようにするため。画面が少ないうちに入れるほど、書き換えが少なくて済む
  - 書き方の決まりは本書9-1、導入の手順とバージョンは本書18-3・18-4
  - 部品は、使う画面を作るときに `add` で足す（順4 で検索の条件のポップアップに dialog を足した）
  - 5軸のスライダーは、shadcn/ui のスライダーを使わず、中身の Base UI のスライダー（`@base-ui/react/slider`）を5軸の部品（`components/culture-axes-field.tsx`）の中で直接組み立てた（順9。PR244）。shadcn/ui のスライダーは「左端から塗る」「目盛りなし」の形で、棒の中に目盛りと真ん中からの線を入れる場所がないため。一度 `add` で入れた `components/ui/slider.tsx` は消した
  - shadcn/ui にない、この画面独自の色は、`app/globals.css` に変数を足して使う（`--highlight`：薄いオレンジ。5軸の真ん中からの線、カルチャーの2点の間の線、学生詳細の比較の「一致」の枠で使う。PR245）。Tailwind では `bg-highlight`・`border-highlight` のように書ける
  - ページ送り（「前へ 1 … 4 5 6 … 10 次へ」）は、shadcn/ui の部品を使わず、ボタンの見た目（`buttonVariants`）と Next.js の Link で自作した（`components/page-nav.tsx`）。必要なのは番号と前後だけで、shadcn/ui の部品は中の `<a>` を Link に差し替える手間があるため
  - Markdown の表示（プチ職業体験の講座の解説・問題。順18）：react-markdown（リアクト・マークダウン）を使う（PR396）。React で Markdown を表示するときに最もよく使われる部品で、文の中に HTML が書かれていても HTML として出さない（安全のため）。部品は `components/markdown-text.tsx` の1か所で、見た目は講座で使う書き方（段落・箇条書き・引用・太字）にだけ Tailwind のクラスを当てる。見た目を整える追加の部品（`@tailwindcss/typography`）は入れない
  - 1つだけ選ぶ丸いボタン（ラジオボタン）は、shadcn/ui の部品を足さず、ブラウザ標準の `<input type="radio">` を `components/form-fields.tsx` の `RadioField` で並べた（順18。プチ職業体験の問題と自己分析の選択）。選ぶ数が少なく、キーボード操作も標準のままで足りるため
- 使う Rails 8 の標準機能
  - 認証：Rails 8 標準の認証の形（認証ジェネレーターが作る形）を使う。ログイン中のセッションを sessions テーブルで持つ
    - ジェネレーター（コードの自動生成機能）は実行せず、ジェネレーターのひな形と同じ名前・同じ形（User・Session・Current・Authentication・SessionsController）のコードを、層ごとに手で書く
    - 理由：ジェネレーターは、モデル・テーブル・コントローラー・認証の仕組みを一度に作るため、層ごとに説明・承認して進められない。また、作られたものの大半を設計に合わせて直す必要がある（下の3点など）
    - メールアドレスの列は、ジェネレーターの `email_address` ではなく `email` にする（API のキー名もすべて `email` のため。本書8-5）
    - パスワード再設定の部品は作らない（本書4-3）
    - 未ログインのときは、ログイン画面へ移動させるのではなく 401 の JSON を返す（本書16-1-6）。ログインの回数制限（3分間に10回）はひな形のまま使い、超えたら 429 の JSON を返す（本書16-3 ①）
  - パスワード：has_secure_password（ハズ・セキュア・パスワード）で暗号化して保存する
  - 画像：Active Storage（アクティブストレージ）。企業・学生のアイコンに使う
  - 裏側の処理（ジョブ）：Active Job（アクティブジョブ）と Solid Queue（ソリッドキュー）。推薦の集計の更新と通知の作成に使う
    - Active Job はジョブの書き方の窓口（Django＋Celery の `@shared_task` と `.delay()` にあたる）、Solid Queue は積まれたジョブを待ち行列に預かる係（Celery のブローカーにあたる）、実行係（`bin/jobs`）は待ち行列から取り出して動かすプログラム（`celery worker` にあたる）
    - 待ち行列は、アプリとは別のデータベースに置く（開発は `backend_development_queue`、本番は `backend_production_queue`。Rails 8 の標準の形。順12。PR291）。実行係は、開発では jobs のコンテナで動かす（本書18-1）

### 3-2. データの考え方

- B-1 応募とスカウト：「やりとり」1テーブルに統合する。「企業-学生」ではなく「募集-学生」で1件。発生元（応募／スカウト）と状態を別の列で持つ
- B-2 チャットの紐づけ：「企業×学生」で1スレッド（募集ごとには分けない）
- B-3 アカウント構造：ログイン情報（メール、パスワード、種別）と、プロフィール（学生／企業）を別テーブルに分ける
- B-4 運営（管理者）：作らない。掲載審査は README で「運用前提・今回はスコープ外」と明記する

### 3-3. 品質の方針

- D-1 テスト：Rails の API（リクエスト）テスト中心。権限の確認と、主要な流れ（登録 → 募集 → スカウト → メッセージ）を1本。推薦の計算は、単体でテストできる部品にまとめる（本書9-4）
  - 道具：RSpec（アールスペック）と、テストデータを作る FactoryBot（ファクトリーボット）。日本の Rails の現場で最も多く使われていて、API のテストを request spec の形でそのまま書けるため
  - テストでも CSRF 対策を有効にする（Rails の標準では、テストのときは切られている）。テストの側で、本物の画面と同じように合言葉の Cookie を取り、`X-CSRF-Token` ヘッダーで送る。この処理はテスト用の共通の関数1つにまとめる
    - 理由：必須のテスト「ログイン画面を初めて開いた人が、そのままログインできる」は、CSRF 対策が有効でないと何も確かめられない。全体で有効にすれば、すべてのテストが本番と同じ条件で動く
  - テストでは、裏側のジョブを実行せず、頼まれたことだけを記録する（`config.active_job.queue_adapter = :test`。開発・本番は Solid Queue）
    - 理由：アイコンの保存で Active Storage が頼むジョブ（画像の解析、差し替え前の画像の削除）に、テストの結果が左右されないようにするため。推薦のジョブ（本書7-5）が頼まれたかを確かめるときにも使う（`have_enqueued_job`）
    - ジョブの中身は、テストの中で `perform_now` で直接動かして確かめる（`spec/jobs/`）
  - テスト用の画像は、ファイルとしてリポジトリに置かず、テストの中で作る（`spec/support/upload_helper.rb`）
  - 必ず入れるもの：ログイン画面を初めて開いた人が、そのままログインできること（本書16-1-7）。他社の番号や、見てよい範囲の外の番号が 404 になること（本書16-1-10）
- D-2 セキュリティ：自分で設計するのは権限制御と個人情報の出し分け。パスワード保存・SQL（エスキューエル）インジェクション対策・パラメータ制限はフレームワーク標準に乗る。ログインの回数制限は Rails 標準機能で入れられれば入れる
- D-3 重さ対策：N+1問題（エヌプラスワン）の回避、外部キーへのインデックス、一覧のページ分け

## 9. 設計・実装のルール（Phase 5 以降で守ること）

### 9-1. 後で変えると大変なものへの対策

- enum は番号を明示して書き、新しい値は末尾に足す
  - 理由：並び順の番号で保存される書き方だと、途中に差し込んだときに既存データの意味がずれる
- マスタは code か name で管理し、削除しない
  - 理由：募集・学生・（Phase 7 の）体験がすべて参照するため、統合・分割すると全データの付け替えが必要になる
  - 非表示が必要になったら、表示するかどうかの列を後から足す
- 「今の会社」を取り出す処理を1か所（ヘルパー（共通の関数））にまとめ、各所で `current_user.company_profile` を直接書かない
  - 理由：将来、1社に複数の担当者を持たせるときに、修正を1か所で済ませるため
  - メッセージの送信者はすでにユーザー単位なので、そのまま使える
- 性格・カルチャーの軸の定義（列名、両端の説明）をコードの1か所にまとめ、軸ごとの処理は「軸の一覧を順に見る」形で書く
  - 順9 で作った置き場所：軸の並びと範囲・確かめは Rails の concern `app/models/concerns/culture_axes.rb`（`CultureAxes::AXES`、`validates_culture_axes`）。学生（personality_）と募集（culture_）の両方が使う。両端の説明の文言は `config/locales/ja.yml` の `culture_axes` で、⑦ が軸の並びどおりに返す（本書16-3 ⑦）。画面側は軸ごとの文言を持たない
  - 順10：カルチャーは判定しないことになった（PR258・PR259）ので、比較の部品には入れていない。募集詳細（⑲）が返す自分の働き方の好み（my_personality_ の5つ）は、`CultureAxes::AXES` を順に見て作る
- 学生と募集の比較（学生詳細。本書16-3 ㉓）の判定は、`app/services/student_job_posting_comparison.rb`（`StudentJobPostingComparison`）の1か所にまとめる（順10）
  - 業界・職種・使用技術の重なりと、稼働条件6項目の一致・不一致・未入力を返す。画面は結果を見て色を付けるだけ（本書16-1-9）
  - 稼働条件の一致の決まりは、検索の本体（SQL の条件）とこの部品（Ruby の if 文）の2か所に書くことになる。どちらも Rails の中で、それぞれテストで守る。検索は「データベースで絞る」、比較は「1件ずつ見比べる」と使い方が違い、1つにまとめるのは難しいため
  - 関連は、読み込み済みのものを `map` で使う（`pluck` でその場で問い合わせない）。窓口が全募集ぶんの関連を最初にまとめて読み込めるようにするため（N+1問題を避ける）
- 稼働条件の選択肢（1／3／6／9／12 など）と検証を、共通のモジュール（Rails の concern（コンサーン））1か所にまとめる
- 推薦のパラメータは、データベースではなく、コードの設定ファイル1か所にまとめる（本書7-4）
- 画面の色は、色の名前（`text-gray-500`、`text-red-600` など）で直接書かず、shadcn/ui の色の変数（`text-muted-foreground`、`text-destructive` など）で書く（本書3-1 A-8）
  - 理由：後で見た目を整えるときに、`app/globals.css` の変数を直すだけで全画面に効かせるため
  - 画面の見出し（h1）は見出しの部品（`components/page-title.tsx`）で出す。ログイン後の画面の幅と余白は、共通の枠（`(main)/layout.tsx`）とヘッダーでそろえる
  - 画面全体の枠（`body`）は中身を縦に並べる flex なので、その直下で左右の余白を自動（`mx-auto`）にする枠には、`w-full` も付ける。付けないと、横いっぱいに広がらず中身の幅まで縮む（順8 の新規登録の画面で起きた）
  - 必須の印（赤い「＊」）と「＊は必須項目です」は、`components/form-fields.tsx` の部品で出す（本書6-4。PR231）
- 同じ項目の入力欄を複数の画面で使うときは、欄を部品に切り出して使い回す（順8）
  - 会社情報の欄（`components/company-info-fields.tsx`）は C1 と C9、学生プロフィールの欄（`components/student-profile-fields.tsx`）は S1 と S9
  - 部品は「値・変えた項目と値の組を渡す関数・誤り・選択肢」を受け取る形にそろえる。変えたときの関数は、`{ about: "…" }` のような組を渡し、使う側が自分の値に重ねる（項目の名前と値を別々に渡す形は、TypeScript の型が合わなくなるため）
  - 順9 で足した共通の部品
    - 5軸のスライダーと見るだけのグラフ（`components/culture-axes-field.tsx`）：値は「軸の名前 → 数」で受け取り、学生の personality_ にも募集の culture_ にもつなげる。軸の名前から列名への対応は、使う側（`student-profile-fields.tsx`・`job-posting-form.tsx`）が持つ
    - メイン／サブの選択（`lib/role-ids.ts` と `components/role-toggle.tsx`）：Rails とは2つの番号の一覧でやりとりし、画面の中では1つのチェックの一覧＋項目ごとのメイン／サブとして扱う。C3 の職種と工程で使う（PR234・PR235）
    - 職種の入力部品（`components/job-category-picker.tsx`）は4か所で共通。メイン／サブを選ぶ形は、使う側が `roles` を渡したときだけ出す
  - 順10 で足した共通の部品
    - 見るだけのカルチャーグラフ（`CultureAxesView`）に、比べる相手（`compare`）を渡せるようにした。渡すと白丸（本体）と黒丸（相手）を重ね、2点の間に線を引く。S6 と C6 で使う（本書6-4）
    - 学生詳細の応募理由の一覧と比較のまとまり（`components/company-student-comparison.tsx`）。学生の値の書き方は、学生詳細のプロフィール（`student-profile-view.tsx` の `workStyleNames` など）とそろえる

#### 9-1-1. 【強み】を後から足すときに作り直さないために

Phase 6 では【コア】を先に通し、【強み】を後から足す（本書11-2）。データベースは42テーブルすべて設計済みなので、【強み】で行うのは列・テーブルの追加（マイグレーション）だけで、設計のやり直しは起きない。ただし次の4か所は、【コア】の段階から最終形で作る。省略すると【強み】のときにコードの作り直しになる。

| # | 場所 | 【コア】で守ること | 省略した場合 |
| --- | --- | --- | --- |
| 1 | 検索の条件（S2・C5。本書7-3） | 条件で結果を減らさず、1件ずつ「合致したか」を付けて返し、画面では境目に区切りを出す。**順4 で S2、順6 で C5 をこの形で作った。順9 で S2 に工程の条件を、条件の一覧に1つ足すだけで入れられた** | 普通の絞り込み（条件に合わないものを消す）で作ると、検索の処理と画面の両方を作り直すことになる |

### 9-2. 処理の決まりごと

- スカウト送信時は、次の4つを1つのトランザクション（まとめて成功か、まとめて取り消しにする処理）で作る
  - やりとり（candidacies）
  - スレッド（まだなければ message_threads）
  - メッセージ（messages）
  - スカウトメッセージ（scout_messages）
  - あわせてスレッドの最後のメッセージの日時（last_message_at）を入れる。スカウト文の送り手は、その募集の企業のアカウント（今は1社1アカウント）
  - 処理は `Candidacy.send_scout` にまとめた（順6）。スカウト文は、トランザクションに入る前に、メッセージのモデルの決まり（空不可・2,000文字まで）で確かめ、エラーを「スカウト文」の名前でやりとりのエラーに写す（`validate_scout_body`。決まりを2か所に書かないため）
- 学生がスカウトにマッチするとき（`candidacy.match_by_student`）は、スレッドを作らない。スカウトを送ったときにもうできているため
- 応募がマッチしたときは、やりとりの更新と、スレッドの作成（まだなければ）を1つのトランザクションで行う
- 新規登録（C9・S9）は、最後の「登録する」で、アカウント・プロフィール・付属情報を1つのトランザクションでまとめて作る。アイコンは登録の直後に別の窓口で送る（本書16-3 ⑤）
  - 処理は、表を持たない「登録」のモデル（フォームオブジェクト。`app/models/registration.rb` と、子の `CompanyRegistration`・`StudentRegistration`）にまとめる（PR226）。Django の「2つの ModelForm を1つのフォームにまとめたもの」にあたる
  - アカウント（users）とプロフィールを両方確かめ、誤りを1つにまとめてから書き込む。メールアドレスと会社名の誤りを一度に返し、片方だけ書き込まれることもないようにするため。誤りの文の項目名は、元のモデルのもの（`Registration.human_attribute_name`）
  - 窓口は「ログインした状態にする処理」（`start_new_session_for`）をブロックで渡し、登録のモデルは書き込みと同じトランザクションの中でそれを呼ぶ（sessions も同じトランザクションで作る）
  - 同時に同じメールアドレスで登録され、データベースの UNIQUE に弾かれたら、メールアドレスの「はすでに登録されています」にする
- 応募・スカウトへのマッチでは、candidacies、candidacy_reasons、reason_mask を同じトランザクションで保存する
- やりとりの操作（応募・マッチ・スカウトなど）は、やりとりのモデル（`app/models/candidacy.rb`）のメソッドにまとめ、窓口はそれを呼ぶだけにする（本書9-1-1 の4。PR204）
  - まだないやりとりを作る操作（応募の `Candidacy.apply`、スカウトの `Candidacy.send_scout`）はクラスメソッド、今あるやりとりを変える操作（企業のマッチの `candidacy.match`、見送り・見送りの取り消し・合格・不合格の `decline`・`undo_decline`・`mark_passed`・`mark_failed`、学生のマッチの `candidacy.match_by_student`）はインスタンスメソッドにする
  - enum の値と同じ名前のメソッドは作らない。enum は値ごとに絞り込み（`Candidacy.scout` など）を自動で作るので、同じ名前のクラスメソッドを作ると、エラーを出さずに上書きしてしまう（PR215）
  - Ruby に最初からある命令と同じ名前のメソッドも作らない。`fail`（raise の別名）を上書きすると思わぬ動きになるので、合格・不合格は `mark_passed`・`mark_failed` にし、URL の `/pass`・`/fail` はルーティングでつなぐ（PR269）
  - 応募理由の確かめ（`validate_reasons`）と保存（`save_reasons!`）は、応募と学生のマッチで使い回す
  - 今の状態ではできないときは `ConflictError`（`app/errors/conflict_error.rb`）を投げ、共通の部品が 409 にする（本書16-1-10。PR205）。押せるボタンの判定（`Candidacy.available_actions_for`）と操作のときの確かめは、同じメソッド（`can_scout?`、`can_match_by_company?`、`can_match_by_student?`、`can_decline?`、`can_undo_decline?`、`can_mark_passed?`、`can_mark_failed?`）を使う
  - 同時に2回押されたときに備え、データベースの UNIQUE に弾かれたら 409 にする。スレッドは「作ってみて、弾かれたら今あるものを使う」（`create_or_find_by!`）で作り、重複させない
- 学生が見てよい募集（掲載中と、自分とやりとりがある募集）は、学生プロフィールのモデルの1か所（`StudentProfile#visible_job_postings`）で決め、募集詳細と応募の窓口はそこから番号で探す。企業側は、自社のやりとりを `current_company.candidacies`（募集を通した多対多）から探す（本書16-1-10）
- プロフィールの保存（C1・S1）は、プロフィール本体と付属情報（企業なら業界・事業形態、学生なら付属テーブル7つ）を1つのトランザクションで保存する
  - 理由：Rails では、保存済みのレコードに多対多の番号の一覧（`industry_ids` など）を代入すると、保存を待たずにその場で中間テーブルが書き換わる。トランザクションで包まないと、会社名が空欄で保存に失敗したのに業界だけが変わる、といった半端な状態が残る
  - 保存の処理はモデルの1つのメソッドにまとめ、窓口はそれを呼ぶだけにする（本書9-1-1 の4。推薦の集計の項目数を保存し直す処理も、ここに足す）
  - そのメソッドの中は、「値を入れて確かめる」（`assign_profile`）と「書き込む」（`write_profile!`）の2つに分ける。新規登録のモデルが、アカウントと一緒に確かめ・書き込むときに、この2つを使うため（順8。PR226）
  - 窓口が受け取ってよい項目の一覧は、プロフィールのコントローラーの定数（`PERMITTED_PARAMS`）1か所に書き、新規登録の窓口もそれを使う
  - 存在しない番号が送られたときは、Rails の標準では「見つからない」（404）になるが、入力の誤りなので 422 で返す。番号がマスタにあるかの確認を自分で書く（本書17-3-4）
  - この確認（マスタにあるか、重複がないか）は、モデルの共通のモジュール（concern（コンサーン））1か所にまとめ、企業プロフィール・募集・学生プロフィールで使い回す。番号の一覧だけでなく、番号1つ（募集の勤務地、学生の大学・学部・学科・在住の都道府県、プログラミング歴の技術）の確認も同じ場所に置く
  - 学生のプログラミング歴のように「行」を持つ付属情報は、送られた行ごとにモデルを作って確かめ、誤りを行の番号付きの名前（`skills[0].years`）で本体のエラーに写す（本書16-3 ⑯）。書き込みは、確かめ終えてからトランザクションの中で「消して作り直す」
- 募集の保存（C3）も、プロフィールと同じく、募集本体と中間テーブル（職種・工程・使用技術・業界・事業形態、求める学年）を1つのトランザクションで保存する。保存の処理はモデルの1つのメソッドにまとめる（本書9-1-1 の4）
  - 処理は `JobPosting#save_posting`。工程は職種と同じ扱い：メインか関われるのどちらかが送られたら、送られなかった側は今の内容を使って「両方に同じ工程がないか」を確かめ、トランザクションの中で「まとめて消して作り直す」（同じ工程がメインから関われるに移ることがあるため。順9）
  - 業界・事業形態は、多対多の番号の一覧（`industry_ids` など）をトランザクションの中で代入する（送られなかったら変えない）
- 推薦の集計の更新（件数・self_weight）と通知の作成は、元の処理のトランザクションが確定した後に、裏側のジョブとして実行する。推薦用のジョブは専用の待ち行列に入れ、1つずつ順番に実行する（本書7-5）
  - 置き場所（順12）
    - 集計のモデル：`StudentRecommendationStat`・`JobPostingRecommendationStat`（本書8-5 F）。項目数の数え直し `refresh_item_counts!` は各モデルに、件数と self_weight の数え直し `refresh_interests!` は共通の部品（concern）`app/models/concerns/interest_stats.rb` に置く。件数と self_weight は、やりとりの表を「学生の列でまとめるか、募集の列でまとめるか」だけが違う同じ計算なので、1か所に書き、どちらの列かを各モデルが指定する（PR292 は採用せず）
    - 「興味」として数えるやりとり（本書7-2 の A(S)・B(P)）は、やりとりのモデルの絞り込み `Candidacy.interests`（応募理由・マッチ理由が付いたもの。reason_mask が空でない）の1か所で決める
    - 応募・マッチのあとのジョブ：`app/jobs/interest_recorded_job.rb`（`InterestRecordedJob`）。集計の数え直しのあとに、通知を作る部品（`RecommendedStudentNotifications`。下の9-4）を呼ぶ（順15）。全体の作り直し：`app/jobs/recommendation_stats_rebuild_job.rb`（下の9-4）
  - 数え直しの書き方
    - どのメソッドも番号の一覧を受け取る（1人分・数人分・全員分を同じメソッドで扱う）。書き込みは upsert（なければ作り、あれば書き換える。Django の `bulk_create(update_conflicts=True)` にあたる）
    - 件数・self_weight の数え直しと項目数の数え直しは、それぞれ自分の列だけを書き換える。別のきっかけで動くので、片方が古い値でもう片方を上書きしないため
    - self_weight は、保存済みの interest_count を使わず、やりとりの表から直接数える。更新の順番によって古い値で計算しないため
    - 項目数は、どの項目が変わったかを見ずに、保存のたびに数え直す（自分の1行だけで軽く、条件を増やすと書き漏らしの危険が出るため）
  - ジョブの積み方と動かし方
    - すべてのジョブの親 `ApplicationJob` に `enqueue_after_transaction_commit = true` を書き、トランザクションの中で `perform_later` を呼んでも、いちばん外側が確定するまで積まない。取り消されたら積まない。待ち行列が別のデータベースにあり、アプリのトランザクションに入らないので、確定前に積むと、実行係が保存前のデータを読んだり、取り消されたデータについて動いたりするため（Django の `transaction.on_commit` をすべてのジョブで自動で行うのにあたる）
    - 推薦用のジョブの待ち行列の名前は recommendation。実行係の割り当て（`config/queue.yml`）で、recommendation はスレッド1・プロセス1にし、それ以外は default を担当させる。すべて（`*`）にすると recommendation も取り出して同時に動くので、待ち行列の名前を並べる。新しい待ち行列の名前を使うジョブを作ったら、ここに足す
    - 失敗したときの自動の再試行は設定していない。失敗したジョブは Solid Queue の失敗の一覧に残り、全体の作り直しで直せる
- チャット画面では、Message に `has_one :scout_message`（ハズワン）を付け、スカウトかどうか・どの募集のものかをまとめて読み込む（N+1問題を避ける）
- メッセージの処理は、スレッドのモデル（`app/models/message_thread.rb`）のメソッドにまとめ、窓口はそれを呼ぶだけにする（やりとりの操作と同じ考え方。順7）
  - 送れるか（`can_send?`）：その企業の募集とその学生とのやりとりに、マッチ以降（`Candidacy.after_match`）が1つでもあるか。チャットの can_send と、送るときの確かめの両方で使う
  - 送信（`post_message`）：送れなければ ConflictError（409）、本文に誤りがあれば保存せずに返す（422）。よければメッセージの保存と last_message_at の更新を1つのトランザクションで行う
  - 学生がマッチできるスカウト（`matchable_scouts`）：学生のチャットの「マッチする」を出すため（PR222）。判定は㉜と同じ `can_match_by_student?`
  - スレッド一覧の並び順（`recent_first`）：last_message_at が空なら作った日時で比べる（SQL の COALESCE。PR221）
  - スレッドは、自社・自分のスレッド（`current_company.message_threads`・`current_student.message_threads`）の中から相手の番号で探す。見てよい範囲の外は 404
- 企業・学生で形が同じ返事は、ビューの共通の部品（`app/views/api/shared/`）にまとめる。メッセージ1件（`_message`）と相手（`_partner`）
  - ビューから「今ログインしている人」を使うときは `Current.user` を使う。`current_user` はコントローラーの中だけのメソッドで、ビューからは呼べないため
- 検索の本体は、窓口から分けて1つのクラスにまとめる。募集検索は `app/services/job_posting_search.rb`、学生検索は `app/services/student_search.rb`。おすすめの上位を選ぶ部品も分ける（`job_posting_recommender.rb`・`student_recommender.rb`。順13。下の9-4）
  - 学生検索の除外（30日、もうスカウトできない学生。本書16-3 ㉒）は、検索の本体の「対象の学生」で行う。人数・合致の群・ページ分け・おすすめ順が、すべて除いた後の学生で計算されるようにするため
  - 条件は、学生の表を結合（join）せず、「番号がこの一覧に入っているか」（サブクエリ）で書く。付属の表を結合すると1人が何行にも増えて件数が狂い、また、結合した絞り込みと結合していない絞り込みは Rails の `and` でつなげないため。表を結合するのは、最終活動の順に並べるところだけ
- 学生詳細（C6）では、自社の全募集ぶんの比較を一度に返すので、比較に使う関連（学生の興味のある業界・興味のある職種・プログラミング歴・出社できる都道府県、募集の業界・職種・使用技術）と応募理由をまとめて読み込む（`includes`。順10。本書16-3 ㉓）。Phase 8 の重さの点検の対象にする
- 仮のデータ（デモ用）を入れる処理は、`db/seeds.rb` と分けて `db/demo/` に置き、画面の操作と同じモデルの処理を通して作る（順10。本書18-6）

### 9-3. アイコン（Active Storage）の実装メモ

- 送り方
  - アイコンだけは、JSON ではなく multipart/form-data で、専用の窓口に送る（本書16-3 ⑩・⑰）
- 形式とサイズの制限
  - PNG・JPEG・WebP だけを受け付け、2MB 程度を上限にする
  - Rails には添付ファイルの検証が標準で入っていないため、モデルに自分で検証を書く
  - 添付と検証はモデルの共通のモジュール1か所に、受け取る処理（ファイルかどうかの確認、添付、返事）はコントローラーの共通のモジュール1か所にまとめ、企業・学生で使い回す
- 一覧での N+1問題
  - 一覧画面では `with_attached_icon` を付けて、アイコンをまとめて読み込む
- 画面側のアイコン欄（`components/icon-field.tsx`）
  - 保存したあとにファイルを選ぶ欄を空に戻すときは、欄を直接つかむ ref（レフ）を使わず、欄に付けた key（キー）の番号を変えて作り直す（PR206）
  - ref を持つ入れ物を描画の中で読むと、書き方の点検（ESLint の react-hooks/refs）が誤りとして止めるため
- Next.js からの転送
  - 画像の URL は `/rails/active_storage/...` という形になる
  - Next.js の rewrites の転送対象に、このパスも含める
- 保存先
  - 手元の Docker 環境では、サーバーのディスクに保存される
  - コンテナを作り直しても消えないよう、保存フォルダ（storage/）を Docker のボリュームに割り当てる
- 画像の縮小
  - 縮小版を作るには、画像処理のライブラリ（libvips（リブヴィップス））を Docker のイメージに入れる必要がある
  - 最初はサイズ上限だけで進め、Phase 8 の重さの点検で必要なら追加する

### 9-4. 推薦の実装メモ

- 推薦の計算は、画面や API から切り離した部品（サービスクラス）にまとめ、単体でテストできるようにする（順13）
  - 上位を選ぶ部品：S2 は `app/services/job_posting_recommender.rb`（`JobPostingRecommender.ranked_ids(学生, [合う群, 合わない群])`）、C5 は `app/services/student_recommender.rb`（`StudentRecommender.ranked_ids(募集, [合う群, 合わない群])`）。返すのは、群ごとの上位100件の番号を f の高い順に並べてつないだ配列だけ（PR295。本書7-5）
  - 検索の本体（`job_posting_search.rb`・`student_search.rb`）は、その配列を PostgreSQL の `array_position` で並べ替えの条件にし、群 → 上位の中の順位（入っていなければ後ろ）→ 新着順（C5 は最終活動の順）→ 番号の順にデータベースで並べる。Django の `order_by(Case(When(id=…, then=順位), …))` にあたる。ページ分けは新着順と同じく、Pagy にデータベースの結果を渡す
  - 計算の部品は `app/services/recommendation/` に置く（Content、計算に使う興味、共起と CF、募集どうし・学生どうしの f、募集×学生の f、パラメータ。本書7-5）。Django でいうと、アプリの中に `recommendation/` パッケージを作るのにあたる
  - 似たもののポップアップの選び方（順14）：C6 は `app/services/similar_students.rb`（`SimilarStudents.ids(学生, 募集)`）、S6 は `app/services/similar_job_postings.rb`（`SimilarJobPostings.ids(募集, 学生)`）。最大5件の番号を並べた順で返すだけで、行の中身と関連の読み込みは窓口が行う（本書7-3・7-5）
    - 稼働条件の判定は、検索の本体の条件を使い回す（PR313）。検索の本体に、稼働条件を検索の条件の形にする `StudentSearch.work_condition_params(募集)`・`JobPostingSearch.work_condition_params(学生)` と、条件だけを渡した候補に当てる `matched_within(候補)` がある。検索とポップアップでは除く相手が違う（C5 は未対応の応募がある学生を残すが、C6 のポップアップは除く）ので、検索の対象（base）ではなく候補を受け取る形にした
  - 通知（順15）：`app/services/recommended_student_notifications.rb`（`RecommendedStudentNotifications.create_for(学生, 募集)`）。似た募集のポップアップと同じ近さ f と稼働条件の判定（`JobPostingSearch.work_condition_params(学生)`。PR324）を使い、会社ごとの代表を PostgreSQL の DISTINCT ON で選んで上から5社にし、1社1件の通知を1つのトランザクションで作る（本書7-3・7-5）。Django の `order_by("company_profile_id", …).distinct("company_profile_id")` にあたる
- 募集どうし・学生どうしの近さ f は、Content と CF の SQL を1本につなぎ、f まで SQL で出す（`Recommendation::Similarity`。PR316）。f を出す SQL を実行せずに文字列で渡す入口（`student_student_sql`・`posting_posting_sql`）があり、ポップアップはこれを問い合わせの中に組み込んで、並べ替えと「上から5件」までデータベースに任せる。Django でいえば、QuerySet を評価せずに `Subquery` として別の問い合わせに入れるのにあたる
- Content の計算は SQL だけで書く（組み合わせごとに1つ。Ruby 版は持たない。本書7-2。PR288）。組み立てた SQL を `select_all` で実行し、重みなどの数は SQL に直接書き込まず、パラメータのファイルから値として渡す。Django の `raw()` にあたる
  - 相手のタグと重なる行だけを索引で引く形にしている。タグの番号から学生・募集を引く索引（興味のある職種・業界、プログラミング歴、募集の職種・技術・業界・工程）は、すべてそろっていることを順13 で確かめた
- 推薦の SQL を書くときの注意（中の段階の実測で見つけた。本書7-5。PR330・PR332）
  - 本体の結合は、渡した番号の一覧（`lefts`・`rights`）から始める。結合する表が多い（既定で8つを超える）と、PostgreSQL は結合の順番を並べ替えず、書いた順に近い形で実行する。表どうしを先に CROSS JOIN して最後に `WHERE … IN` で絞ると、渡した人数に関係なく「表全体 × 表全体」の組を作ってしまう
  - 番号の配列（数千個）を `IN (…)` にそのまま入れない。候補の1行ごとに一覧を端から照らし合わせることがある。先に1回だけ表の形にしてから（`AS MATERIALIZED`）照らし合わせる。1回しか使わない下ごしらえ（CTE）は、`MATERIALIZED` を書かないと本体に埋め込まれる
  - 小の段階では表が小さいので、どちらも目立たない。推薦の SQL を変えたら、中の段階で速さの診断（下の9-4-1）を流して、相手の数に比例しているかを確かめる
- 1回の表示の工程の区切り（Content、行動の近さと F1、並べ直し）に、計測用の印（`ActiveSupport::Notifications.instrument`）を付けている。下の9-4-1 の実測のためのもので、Django のシグナルを送るのに近い（PR307）
- ダミーデータを大量に作るコマンドを用意し、処理時間を実測する（下の9-4-1）
- 全体の作り直し（stats の数え直し）は、手動で実行するコマンドとして用意する（本書7-5）
  - 順12 で作った：ジョブ `RecommendationStatsRebuildJob`（全学生・全募集を1,000件ずつ `in_batches` で取り出し、項目数と件数・self_weight を数え直す）と、それを待ち行列に積むコマンド `bin/rails recommendation:rebuild`（`lib/tasks/recommendation.rake`。`bash dev.sh rebuild`）
  - 手動のコマンドは待ち行列に積む（応募のジョブと同じ待ち行列で1つずつ動くので、同時に動いて古い値で上書きしない）。仮のデータ（`db/demo/loader.rb`）と試しのアカウント（`db/seeds.rb`）を入れたあとは、その場で実行する（`perform_now`。画面の操作がない準備の時間のため）
- パラメータの調整（Recall@K や nDCG による評価）は後回し

- 小 → 中でデータが数十倍になったとき、時間が**何倍になったか**を見る。データと同じくらいなら候補の件数に比例（想定どおり）。それよりずっと大きければ、二乗で効いている場所があるので、速さの診断で部品ごとの増え方と実行計画を見る（中の段階で2か所見つかり、直した。本書7-5）
- 大の段階は、「固定の分 $a$ ＋ 1件あたりの分 $b$ × 件数」の $a$ と $b$ を出して見積もる。小と中の2点では、中で見つかった重さのように、増え方が比例から外れていると使えないので、中の段階の中で相手の数を変えた診断から出す。作業用のメモリに収まらずディスクを使い始めていないかも、実行計画で確かめる

### 9-7. ブランチとコミットの運用

ブランチとコミット

- ブランチの作成・コミット・main への取り込みは、開発者が自分で判断して行う。細かい運用ルールは設けない
- AI は、指示がない限りブランチの作成やコミットをしない
- 秘密の情報（`.env`、`config/master.key`）は入れない。`.gitignore` で除外してある

改行コード

- ルートの `.gitattributes` で `* text=auto eol=lf` を指定し、**改行コードを LF にそろえる**
- 理由：Windows で編集すると行の終わりが CRLF になる。Rails の起動スクリプト（`bin/docker-entrypoint` など）が CRLF のまま Docker（Linux）に入ると、「not found」という分かりにくいエラーで止まるため
