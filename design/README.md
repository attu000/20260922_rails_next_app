# 設計書

エンジニア職の長期インターンを探す学生と、学生を探す企業をつなぐ「募集・スカウトサービス」の、**設計書**を置いているフォルダです。

- 実装は、この設計書をコードに翻訳する形で進めました。設計書は、AI が読めばそのまま実装に移れる具体さになるまで、相談と更新を繰り返しています
- 実装の途中で設計が変わったときは、コードだけを合わせず、先に設計書を直してから実装しています。そのため、設計書は今のコードと一致した状態です
- 設計書は網羅的に書いているので、全体像と工夫点を短く知りたいときは、ルートの [README.md](../README.md) と [docs/](../docs/) を先に読んでください

## フォルダの見方

```
design/
├── README.md      … このファイル（設計書の読み方）
├── CLAUDE.md      … 設計書を更新するときの、AI への指示書
└── designs/       … 設計書の本体（常に最新の状態に保つ）
```

- 話し合いの記録（議事録）は、設計にも実装にも関わるので、このフォルダではなくルートの [minutes/](../minutes/) に置いています
- 議事録1〜4 の内容は、designs/ に統合済みです。minutes/ には、議事録5 以降を置いています

## 初めて読むときのおすすめの順番

1. サービス概要_コンセプト.md：何のためのサービスか、用語の意味
2. ページ設計.md：どんな画面があり、どう移動するか
3. その他決め事.md の5章：画面をまたぐルール（やりとり・マッチ・見送りなど）
4. データベース.md：データの持ち方
5. 処理設計_類似度.md：おすすめの仕組み（読み飛ばしても全体はつかめます）
6. 技術構成.md：使う技術と、実装のときに守るルール
7. API設計.md・権限_バリデーション.md：画面と Rails のあいだのやりとりの決まり
8. 未決内容.md：残っている論点

## 設計の進め方

- AI は、提案・反論・主張に **PR1、PR2 …** の通し番号を付けます（Proposal の略。学生側の画面番号 S1〜S12 と区別するため）
- 開発者は、番号ごとに承認か反論をします。触れなかった番号は「未決」とし、設計書にもコードにも入れません
- 決まったことは designs/ に反映し、古い内容は新しい内容に置き換えます。途中で変わった点は、その他決め事.md の13章に「旧 → 新」の形で残します
- 話し合いのたびに、「決めたこと」と「決めなかったこと（未決・保留）」を minutes/ の議事録に残します
- 設計書を更新するときの決まりは [CLAUDE.md](CLAUDE.md) にあります

### その他の表記

| 表記 | 意味 |
| --- | --- |
| C1〜C11 | 企業側の画面番号 |
| S1〜S12 | 学生側の画面番号（S10 は欠番） |
| 【コア】【強み】【仕上げ】【後付け】 | 段階タグ。実装の優先順（ページ設計.md の 6-4） |
| 順0〜順19 | 実装した順番（未決内容.md の 11-2） |
| 募集／応募 | 募集は企業が出すもの、応募は学生がするもの（厳密に呼び分ける） |
| やりとり | 「募集×学生」の組み合わせ1件。応募・スカウトのどちらから始まっても同じ |
| マッチ | 企業と学生の双方が意思表示して、会話ができるようになること（採用の決定ではない） |
