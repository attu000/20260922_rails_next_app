# 設計書を更新するときの指示書

このファイルは `design/` の中を触るときにだけ効く、**追加の決まり**です。
プロジェクト全体の決まり（役割、私について、開発のテーマ、ブランチ運用、PR 番号の扱い、しなくていいこと）は、ルートの [CLAUDE.md](../CLAUDE.md) にあります。

## 1. このフォルダの役割

`design/` は、このサービスの**設計の記録**を置く場所です。

| フォルダ | 中身 | 更新するか |
| --- | --- | --- |
| `designs/` | 設計書の本体。**常に最新の状態に保つ** | する |
| `minutes/` | 議事録。話し合いごとに1本ずつ積み上げる | 追加する（過去分は直さない） |
| `premise/` | 出発点の資料（課題文、当初の進め方） | **しない**（Git 管理外） |

- 設計書は「AI が読めば、そのまま実装に移れる」具体さを保つ。
- 設計書と実装が食い違ったときは、どちらを直すかを必ず確認する。黙ってどちらかに寄せない。

## 2. 設計ファイルの更新

**指示されるまで行わないこと。**

- 決定事項を、該当する設計ファイルに反映する。
- **古い情報は新しい情報に置き換える。** 「以前はこうだった」を本文に残さない。
- 途中で変わった点は、その他決め事.md の13章に「旧 → 新」の形で残す。
- 章番号は `designs/` 全体の通し番号。各ファイルの冒頭にある対応表は、章が増えたら全ファイルで更新する。
- ファイルをまたぐ相互参照（「本書X-Y」）があるので、章番号を変えるときは参照元も直す。

## 3. 議事録の記載

**指示されるまで行わないこと。**

- 置き場所：`minutes/NNN-〇〇について.md`（例：`minutes/010-環境構築について.md`）
- 書く内容
  1. 話し合ったこと
  2. **決めたこと**（PR 番号・結果・内容の表）
  3. **決めなかったこと（未決・保留）**。未決の PR 番号は、番号と内容をあわせて記載する
  4. 反映した設計書
  5. 次にやること

## 4. 設計の相談に乗るときの方針

1. **現実的なベストプラクティスを検討する。** 設計や技術選定は「一般的」であること。挑戦的で、現場での実現可能性や安定性が低いアルゴリズム・開発手法はできるだけ避ける。
2. **論理的かつ中立的に判断する。** 過剰な反対も、安易な賛成もしない。
3. **質問形式で意向を問う。** 反論・提案・主張がある場合は断言せず、「〜してはどうでしょうか？」のように意向を確認する。
4. **通し番号を振る。** 反論・提案・主張には `PR1`、`PR2` … と番号を振る。会話全体で通し番号とし、過去の番号と重複させない（設計フェーズで PR114 まで使用済み）。
5. **触れられなかった番号は未決。** 承認ではないので、設計書には反映しない。議事録に残す。
