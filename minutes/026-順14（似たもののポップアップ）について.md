## 1. 話し合ったこと

- 順14 の全体像：学生詳細でスカウトを送った直後の「この学生に似た学生」5人と、募集詳細で応募した直後の「この募集に似た募集」5件。選び方（候補すべての f → 除外 → 稼働条件に合うものから f の高い順 → 足りなければ合わないものから補う → それでも足りなければある分だけ）は設計書にあり、近さの部品は順13 のものを使う
- 開発者の方針「今の段階から、できるかぎりデータベースの中で検索を済ませたい。学生のおすすめをするときも、段階的な検索（1次検索 → 並べ直し）が必要か。10万人分の f を普通に計算するのは重いのでは」：AI は、段階的な検索は要らないと説明した
  - 学生検索で段階が要ったのは、募集×学生の f に I・U（1人ごとに重い計算）が入るため
  - 学生どうしの f は、内容の近さ（全員分を SQL で出す。学生検索の1次検索の最初の手順と同じ計算）と行動の近さ（0 にならないのは最大4,000人）を混ぜるだけで、絞る必要がない。内容の近さの上位の人を知るには結局全員分を計算するので、絞っても軽くならない
  - 重いのは、10万人分を Rails に読み込んで Ruby で混ぜる部分。混ぜ合わせを SQL に移せば、Rails が受け取るのは5件だけになる
- 開発者の問い「PR316 で早くなるのか。そこまで変わらないなら、やらなくてもいいのでは。Rails が受け取るのが減り、結果早くなるのか」：AI は、ポップアップでは大きく変わり、おすすめ順の並べ直しではほぼ変わらないと答えた
  - 今の作りのままだと、10万行の受け取り、1行ずつの入れ物づくり、件数を読むための「番号10万個を並べた問い合わせ」（数百KB の SQL）、10万行の並べ替えが Rails 側で起きる。見積もりで、SQL に移さない場合は0.3〜1秒、移せば数十ミリ秒の上乗せ
  - 並べ直し（100件 × 200人ほど）は、どちらでも変わらない。乗り換えるのは、同じ式を Ruby と SQL の2通りに書かないため
  - 「ポップアップだけ SQL にして2通りを受け入れる」案も示したうえで、AI は共通の部品ごと SQL にする形をすすめ、開発者が了承した
- 開発者の問い「PR320 について、そもそも似た相手が0件のときでも出す（補充する）という話にしていなかったか」：AI は、補充は「稼働条件に合う相手が5件に満たないとき」に合わない相手から足す話で、0件は「候補そのものがいない」ときだけ起きると説明した。本番の人数ではまず起きず、仮のデータのような少人数で起こりうる

### 3-1. AI が補ったこと

14-1a（混ぜ合わせを SQL に）

- 重み $c(n) = n \div (n + \lambda)$ の式は、SQL（学生どうし・募集どうしの重み）と Ruby（おすすめ度 f(P, S) の重み）の2か所に書く。おすすめ度は並べ直しの100件ほどにしか使わず、SQL に移しても速くならないため Ruby に残した。$\lambda$ はどちらもパラメータのファイルから読む
- 行動の近さがない組は、つなぐときに0として混ぜる（今までの Ruby の扱いと同じ）
- 呼び方と返すもの（組ごとの結果の配列）は変えない。おすすめ順の並べ直しのコードを触らずに乗り換えるため

14-1b（5件を選ぶ部品）

- 本人（似た学生ではスカウトした学生、似た募集では応募した募集）も、はっきり候補から除く。スカウト・応募の直後ならやりとりがあるので自然に外れるが、窓口はいつでも呼べるため
- 変換では、相手の側の空欄の項目は条件に入れない。勤務形態は3つとも可能なら入れない。土日OK は学生の項目にないので入れない（13-5 のボタンと同じ）
- 部品は番号だけを返し、行の中身と関連の読み込みは窓口が行う（検索と同じ分け方）
- 部品の置き場所は、おすすめ順の部品（`JobPostingRecommender` など）と同じく `app/services/` の直下

14-2（窓口）

- 窓口のコントローラーは、学生詳細・募集詳細に足さず、別のコントローラーに分けた（学生・募集の下の別の一覧として。チャットと同じ形）。URL は設計書のまま
- 確かめる順は、募集の番号がない（422）→ 他社の募集（404）→ ない学生（404）
- 返事に matched（条件に合うか）は付けない（ポップアップに区切りを出さないため）
- 選んだ順のまま読むのに、Rails の `in_order_of` を使う

14-3（画面）

- 2つのポップアップに共通の一覧の枠を、別のファイル（`components/similar-list.tsx`）に分けた。説明では新規3ファイルとしていたが、4ファイルになった
- 行のリンクを押したら、ポップアップを閉じてから移る。URL の番号だけが変わる移動で画面が作り直されない場合に、ポップアップが次の画面に残らないように
- ポップアップは、窓口を開いているときだけ呼ぶ。取ってくる間は「読み込み中…」、取れなかったら Rails の一言を出す
- ポップアップは、スカウト・応募のポップアップの外に置く。送ったあとは元のボタンごと消えるため
- 応募完了のポップアップの募集の行に業界などの名前を出すため、募集詳細の状態の部品に選択肢の全体を渡すようにした

14-4（実測）

- ポップアップは、学生5人と募集5件を1組ずつ組にして、5組 × 5回を測る
- 1本の問い合わせで推薦の部品の印を通らないので、工程の内訳は出さず、全体の時間と SQL の本数だけを出す

## 4. 途中でわかったこと

| わかったこと | 対処 |
| --- | --- |
| 14-1a で足したテストが、SQL の文法の誤りで失敗した。問い合わせの中の結果に付けた別名 `similar` が、PostgreSQL の予約語（`SIMILAR TO` で使う言葉）だった | テストの別名を `pairs` に変えて通った。書き換えた本体の問題ではなかった（ほかの621件は通っていた） |
| 大きな規模の見積もり方：各場面の時間は「人数に関係ない固定の分 $a$」＋「1人あたりの分 $b$ × 候補の数 $N$」の形になる。似た学生のポップアップでは、内容の近さと稼働条件の判定・並べ替えが $N$ に比例し、行動の近さは興味の数の上限で頭打ち、行の読み込みは5件で一定 | $a$ と $b$ は測るしかない。小の段階（$N$ ≒ 120）では $b \times N$ がばらつきに埋もれるので、人数の違う2点目として中の段階を測り、2点から $a$ と $b$ を出して運用規模を見積もる。人数が増えると、作業用のメモリに収まらずディスクを使い始める、処理のやり方が切り替わる、ということが起きうるので、中の段階では実行計画（`EXPLAIN ANALYZE`）も見る。行動の近さと並べ直しは、人数ではなく1人あたりの興味の数で増え、上限で止まる（測定用のデータは1人3件で、上限まで届いていない）。処理設計_類似度.md の 7-5 と技術構成.md の 9-4-1 に書いた |
| 小の段階の実測（14-4）：似た学生のポップアップ 0.03秒（SQL 5本）、似た募集のポップアップ 0.04秒（SQL 10本）。どちらも目安（1秒以内）に十分収まり、5件の行ごとに SQL が増えていない（N+1 なし）。似た募集の SQL が多いのは、業界・事業形態が中間の表を通すなど、行の関連が多いため | 処理設計_類似度.md の 7-5 に記録した |
| 同じ実測で、おすすめ順は0.15〜0.25秒で、順13 の値とばらつきの範囲で同じだった。並べ直しの SQL は、群1つあたり11本から7本に減った（近さ f を3本から1本で出すようになり、I と U の2か所で2本ずつ減った）。時間が縮まないのは、減った分がほぼ固定のコストで、小の段階では人数に比例する部分が見えないため | 7-5 の実測の表を、測り直した値に置き換えた |
