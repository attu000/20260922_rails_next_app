### 2-5. 決めた細部

- `return_to` の確認は「`/company/` か `/student/` で始まるか」の1つにまとめ、「`/` で始まるアプリ内のパスだけ」と「種別と先頭が合っているときだけ」の2つの決まりを同時に満たす（`//別のサイト` や `javascript:` も捨てられる）
- 画面側は、ログイン後の画面どうしを移るたびに /api/me を呼び直す。Next.js では画面を移っても共通の枠が作り直されないため、設計書の「すべての画面で、開いたときに呼ぶ」に合わせた
- rails-i18n の「はすでに存在します」を、設計書（17-3-6）の「はすでに登録されています」に合わせた
- 最終活動日は、その日の最初の1回だけ、`update_column`（検証を通さず、更新日時も変えない）で書き込む
- `/api/` の URL に `defaults: { format: :json }` を付け、ブラウザのアドレス欄から開いても JSON のテンプレートを使う
- `dev.sh` は `bash dev.sh <コマンド>` で動かす（実行の権限が要らず、Windows・Mac・Linux で同じ打ち方になる）。Windows では Git Bash で実行する

## 3. 進め方について決めたこと

- ブランチの運用は開発者が行い、細かいルールは設けない。AI は指示なくブランチの作成やコミットをしない（本書9-7）
- コマンドは基本的に開発者が打つ。AI は説明とファイルの作成を受け持つ
- 実装は、層ごとの小さなサブステップに分け、「説明 → 承認 → AI が書く → 開発者が実行」を繰り返す。説明は**触るファイルの一覧（新規／変更と、その数）から始める**
- Phase 6 も同じ進め方にする

## 4. 途中でわかったこと

| わかったこと | 対処 |
| --- | --- |
| json 3.0 と Rails 8.1.3.1 の組み合わせで、Cookie を読むと 500 になる（Rails の課題 #58784。修正 #58601 は版としてまだ出ていない） | PR131 で固定。Phase 8 で外せるか確かめる |
| Windows 側のファイルを Docker で読むと、Turbopack が変更に気づかない。ポーリングの設定も効かない | PR130 で webpack とポーリングに切り替え |
| Next.js は転送するとき、元の住所を `X-Forwarded-Host` に、ブラウザの IP アドレスを `X-Forwarded-For` に入れる | Rails の Origin の確認は追加の設定なしで通る。ログインの回数制限はブラウザごとに数えられる（sessions の IP アドレスで確かめた） |
| 開発中の Next.js は、各画面を初めて開いたときに組み立てるので、初回は十数秒かかる | 本番では起きないので対処しない。遅さが妨げになれば WSL2 側に移す |
| 存在しない画面の URL では、ログイン後の枠が効かず 404 になる（確認の手順の誤りとして見つかった） | 枠は実際にある画面にだけ効く。Phase 6 で画面を作れば、その URL でもログイン画面へ移るようになる |
| PowerShell で `bash` と打つと WSL の bash が動き、Docker を使えないことがある | `dev.sh` は Git Bash で実行すると README と開発環境.md に書いた |
