## 3. 決めたこと

### 3-1. 窓口の作り方

| 番号 | 結果 | 内容 |
| --- | --- | --- |
| PR202 | 承認 | 学生詳細の「押せるボタン」（available_actions）は、窓口ができている操作だけを返す。順5 は「マッチする」だけ。スカウトは順6、見送る・見送りを取り消す・合格・不合格は順11 で足す。状態遷移表の判定は最初から1か所（`Candidacy.available_actions_for`）にまとめる |
| PR204 | 承認 | 応募とマッチの処理を、やりとりのモデルのメソッドにまとめ、窓口は呼ぶだけにする。まだないやりとりを作る応募はクラスメソッド（`Candidacy.apply`）、今あるやりとりを変えるマッチはインスタンスメソッド（`candidacy.match`）。順1〜3 の保存（`save_posting` など）と同じ形で、順12 でジョブを呼ぶ1行を足すだけで済む |
| PR205 | 承認 | 「今の状態ではできない」は `ConflictError` として投げ、エラーの返事の共通の部品（`error_responses.rb`）の1か所で 409 にする。404（見つからない）と同じ仕組み。もう1つの案（処理が「成功／409／422」を返し、窓口ごとに分ける）は、スカウト・マッチ・メッセージの窓口ごとに同じ分かれ道を書くことになるため採らなかった。開発者の求めで、Django の `get_object_or_404` と比べて説明し直した |

- 確かめる順番は「番号（404）→ 状態（409）→ 入力（422）」。終了した募集への応募は、理由を直しても通らないため
- 同時に2回押されてデータベースの「1件だけ」の決まりに弾かれたときも 409。スレッドは「作ってみて、弾かれたら今あるものを使う」で作る
- 押せるボタンの判定と、操作のときの確かめは、同じメソッド（`can_match_by_company?`）を使う
- 募集の番号（job_posting_id）を送らなかったときは 404 ではなく 422（設計書の「必須のパラメータがないときは 422」に合わせた）

## 4. 進め方について

- サブステップの説明の疑似コードを、Ruby の形に寄せたものから、**自然言語に寄せた形**（クラスの中に変数とメソッドを並べ、それぞれに役割を日本語で添える）に変えた。メソッドには `def 名前() -> つまり何を返すか` の形で返り値を書く。開発者がルートの CLAUDE.md の7章に見本を載せた
- 当初の 5-4（企業の窓口）は、窓口が3つでファイルが17個になるため、5-4（候補者一覧）と 5-5（学生詳細とマッチ）に分けた。画面側は 5-6〜5-9、通しの確認は 5-10 になった
- 書き方の点検は、`bash dev.sh lint`（画面側）と `docker compose run --rm -T backend bin/rubocop`（Rails 側）の2つをセットで行う
- 設計書の書き換えと議事録は、PR208・PR209 と企業側のマッチ理由の未決を除き、順5 の最後にまとめて、開発者の指示を受けてから行った
