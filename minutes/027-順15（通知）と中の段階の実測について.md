### 3-1. AI が補ったこと

15-1（表・モデル）

- 受け取る人の列だけの索引は作らない。（受け取る人, 作った日時）の索引の先頭の列が同じ役目をするため（メッセージの表と同じ考え方）
- 既読にするメソッドは、使う窓口と一緒に 15-3 で足した

15-2（通知を作る部品）

- 会社ごとの代表は、稼働条件に合う募集が先 → 近さ f の高い順 → 新着順 → 番号の大きい順の先頭。代表を同じ順で並べ直して上から5社。どちらもデータベースの1本の問い合わせで行う（PostgreSQL の DISTINCT ON と、その結果を外側から読む問い合わせ）
- 本文は「（その会社の募集のタイトル）に合いそうな学生がいます」。移動先は、その募集のタブを選んだ状態の学生詳細
- 5社分の通知は1つのトランザクションで作り、途中で失敗したら1件も残さない。まとめて入れる方法（`insert_all`）ではなく1件ずつ保存し、モデルの確かめを通す
- ジョブの中では、集計の数え直しのあとに置く（近さの重みに数え直した件数を使うため）
- ジョブの説明を書き直した：数え直しは何度実行しても同じ結果。通知は PR322 で同じ会社に二度届かないが、万一2回動けば2回目は次の会社に届く。ただし、ジョブを積むのは2か所で1回ずつ、失敗しても自動では再実行しない設定で、通知は最後の工程なので、心配はほぼない
- 30日以上活動のない学生には作らない（応募・マッチの直後なので、ふつうは活動中）

15-3（窓口）

- 通知は会社ではなくアカウント宛てなので、「今の会社」のヘルパーではなく、ログイン中の人の通知から探す（1社のアカウントは1つなので、自社宛てと同じ意味）
- 1行の返事に、対象の学生の列は入れない（通知先を選ぶためにだけ使うため）
- 未読件数の数え方は `User` のメソッドにまとめた。ログイン中の人の返事のテンプレートは、ログイン・新規登録と共通なので、そこにも入る

15-4（画面）

- 未読の行は、背景色と丸い印に加えて本文を太字にし、画面の読み上げ用に「未読：」を入れた（画面には出ない）
- 行を押して既読にする送信に失敗したら、画面を移らずに一覧の上に一言を出す。送信中はほかの行とボタンを押せなくする
- 「すべて既読にする」のように画面を移らない操作のあとは、ヘッダーの件数を取り直す（画面を移るときは、共通の枠が取り直す）
- 未読が0件なら「すべて既読にする」を押せなくする

診断・直し

- 診断では、相手を番号の配列ではなく問い合わせの形で渡す（実際の画面と同じ計画にするため）。ただし並べ直しの U だけは、実際と同じく配列で渡す
- 並べ直しの対象の募集は、応募の多い順（応募者が上限に近い、重い場合）
- 行動の近さの左の集まりは、1人・1件か多くても100件で短いので、PR332 では変えなかった

## 4. 途中でわかったこと

| わかったこと | 対処 |
| --- | --- |
| 通知ができた会社を確かめるコマンド（`bin/rails runner '…'`）が、PowerShell で失敗した。PowerShell（Windows PowerShell 5.1）は、外の exe に文字を渡すときに中の `"` を消してしまうことがあり、Ruby に文の一部が届かなかった | `"` を使わない書き方（`p [ … ]`）にしたコマンドを出した。長い Ruby をコマンドに直接書かず、ファイルにして動かす方が確実なので、診断はコマンド（`bench-diagnose`）にした |
| 通知ができたことで、測定用・仮のデータを入れ直すと外部キーに弾かれて止まること、測るたびに通知が増えて仕事の量も変わること | PR327・PR328（15-5）で直した |
| 小の段階の実測（15-5 のあと）：応募・マッチのジョブが約27ms から約85ms（SQL 21本）になった。通知先を選ぶ問い合わせ（全募集との近さ f と会社ごとの代表選び）と5件の保存の分。ほかの場面はばらつきの範囲で同じ | ジョブは裏側で動くので、応募した学生を待たせない |
| 中の段階の実測（PR308。学生5,000人・募集1,000件・応募50,000件）：募集一覧のおすすめ順 10.4秒／24.0秒（条件なし／あり）、学生検索のおすすめ順 26.7秒／51.9秒、似た学生のポップアップ 9.1秒、似た募集のポップアップ 0.89秒、ジョブ 0.59秒、全体の作り直し 2.1秒。小の段階から、学生が42倍・募集が9倍なのに、時間は最大で240倍になった。行動の近さは上限が効いていて問題なかった | データ量に比例する以上に重いので、「a ＋ b × 件数」で運用規模を見積もることはできないと判断し、原因を部品ごとに調べた（PR329・PR331） |
| **原因1（内容の近さ）**：実行計画の中で、学生どうしで 25,220,484組（学生の表の全員 5,022人 × 5,022人）、募集×学生で 5,142,528組、募集どうしで 1,048,576組を作っていた。渡した人数（1人 × 5,000人など）に関係なく、表全体どうしの組を作ってから最後に絞っていた。結合する表が多い（既定で8つを超える）と、PostgreSQL は結合の順番を並べ替えず、書いた順に近い形で実行するためと考えられる。小の段階では表が小さかったので目立たなかった。運用規模なら、学生どうしで100億組になり終わらない。あわせて、見積もりが重いために JIT が動き、その変換だけで2.4〜3.3秒かかっていた | PR330 で、番号の一覧から結合を始める形に直した。組の数が渡した分だけになり、内容の近さは 17.4秒 → 0.06秒（学生1人 × 5,000人）など。JIT も動かなくなった |
| **原因2（行動の近さ）**：募集一覧の並べ直しの U の近さ f（学生1人 × 応募者4,767人）が1.2秒かかっていた。同じ人数でも、相手を問い合わせで渡すポップアップの形なら 0.09秒。右の集まりを番号の配列で渡すと `id IN (…4,767個…)` になり、PostgreSQL が候補の学生1人ごと（865回）に、この一覧を端から照らし合わせていた（1回1.25ms）。候補の数 × 一覧の長さで重くなる | PR332 で、右の集まりを先に1回だけ表にしてから照らし合わせる形に直した。U の近さ f は 1.2秒 → 0.13秒、並べ直し全体は 1.5秒 → 0.34秒 |
| 直したあとの中の段階：募集一覧のおすすめ順 0.38秒／0.62秒、学生検索のおすすめ順 0.46秒／0.66秒、似た学生のポップアップ 0.09秒、似た募集のポップアップ 0.05秒、ジョブ 0.11秒、全体の作り直し 2.2秒。診断では、どの部品も相手の数にほぼ比例し、JIT も動いていない | ― |
| 運用規模（学生10万人・募集1万件）の見込み（中の段階の診断の a と b から。データが増えても実行計画が変わらない前提）：内容の近さは学生1人あたり約0.0095ms（固定の分 約13ms）で、10万人で約1.0秒。似た学生のポップアップ 約1.2秒、学生検索のおすすめ順 約1.5〜2秒、募集一覧のおすすめ順 約0.5〜1秒、似た募集のポップアップ・通知のジョブ 約0.2〜0.3秒 | 爆発的に膨れる部分はなくなった。ただ、学生10万人全員を相手にする2つ（似た学生のポップアップ、学生検索）は、設計書の見積もり（0.3〜0.6秒、0.4〜1.0秒）の2倍前後になる見込み。「全員の内容の近さを毎回出す」作り（PR285・PR316）のそのままの重さで、縮めるなら作りを変えることになる（例：タグが1つも重ならない学生を先に外す）。AI は、Phase 8（重さの点検）で扱うのが順当として、今すぐ直す提案はしなかった |
