## 1. 話し合ったこと

- 開発者の案の計算量：どこにどれくらいの時間がかかるか
- 1次検索の重さを減らす方法（開発者の案「①pj ごとに、その応募者たちが応募した募集の集合を保持する」の評価を含む）
- 1次検索を内容の近さだけにする案と、候補を2つの経路から集める案
- 保持するデータ、検索の式、更新の方法のまとめ
- 項目数の列が要る理由、行動の2つの項が同じつながりを数えていること、リランキングの Content をデータベースで計算できるか
- 上限を設けない場合の手当と、101件目以降の並び

## 2. 開発者の案と、その評価

### 2-1. 最初の案

- 検索：「募集Pと学生Sの内容の近さ」＋「Pに応募した学生たちと S の近さ」＋「S が応募した募集たちと P の近さ」
  - 1次検索：内容の近さと、2つの共通数の平均に重みを付けて上位100人に絞る
  - リランキング：上位100人について、学生どうし・募集どうしの近さ（内容＋行動）の平均を使って並べ直す
- 更新：応募のたびに、件数と、学生どうし・募集どうしの共通数を足す。プロフィールの更新では何もしない
- 保持：件数、学生どうし・募集どうしの共通数（0でないものだけ）

### 2-2. AI の見積もり（運用規模のいちばん重い場合）

| 場所 | 件数 | 時間の目安 |
| --- | --- | --- |
| 1次検索の内容の近さ（学生10万人） | 10万組 | データベースで0.2〜0.5秒。Rails に読み込むと数秒 |
| 1次検索の行動の近さの集計 | 約80万行 | 0.3〜0.8秒。保存した共通数を使っても減らない |
| リランキング | 約2.2万組 | 0.2〜0.6秒 |
| 合計 | | 約0.7〜1.9秒（1秒を超える可能性が高い） |
| 更新（応募1件） | 約220行 | 0.01〜0.05秒（とても軽い） |
| 学生どうしの共通数の保存 | 最大 約2億行 | 15〜20GB |

- 開発者の式は、リランキングの分（22,100N ＋ 22,000M）だけで、1次検索で10万人全員に点数を付ける分が入っていなかった
- 案は「更新を軽く、検索を重く」する方向に重さを移したもの

### 2-3. 1次検索を軽くする案の検討

- 開発者の案①（募集ごとに「その応募者たちが応募した募集の集合」を保持する）：回数付きで持つと、中身は募集どうしの共通数と同じ
  - 開発者の疑問「その集合をデータベースから取ってくるのが難しいということか」に対して、AI は次のように説明した。取ってくるのは1回・約3,800件で簡単。重いのは、その集合を**10万人それぞれの応募と突き合わせる**部分（約76万〜200万行）で、①ではここが減らない
  - 逆側の「学生ごとに、その応募先に応募した学生の集合」を保持する案も、企業の学生検索では10万人分を読むことになり効かない（学生の募集検索では効く）
- 開発者の案「1次検索は内容の近さだけにして、リランキングで行動を使う」：速いが、内容の近さで上位に入らなかった学生は、行動の近さがどれだけ高くても出てこない。「行動データが増えるほど行動を重視する」方針とぶつかる
- そこで AI が、候補を内容と行動の2つの経路から集める案（PR282）を出し、採用した

## 3. 決めたこと

### 3-1. 検索の方式

| 番号 | 結果 | 内容 |
| --- | --- | --- |
| PR274 | 承認 | 1次検索の行動の2つの項（「Pに興味を示した学生たちとの共通数」と「S が興味を示した募集たちとの共通数」）は、同じ「S → 募集 ← 学生 → P」のつながりを、学生ごと・募集ごとにまとめて数えているだけなので、1回の集計で済ませる |
| PR277 | 承認 | 1次検索の Content(P, S) はデータベースで計算する（のちに PR288 で、すべての Content に広げた） |
| PR282 | 承認 | 企業の学生検索の1次検索は、「Content の上位1,000人」（内容の経路）と「P と行動が近い上位20件の募集に興味を示した学生」（行動の経路）を合わせた候補だけについて行動の近さを数え、上位100人に絞る。学生の募集検索は、募集が1万件なので全募集を正確に計算する。これにより、学生どうし・募集どうしの共通数を保存する必要がなくなった |
| PR284 | 承認 | 1次検索の点は $F_1 = w_C \cdot \mathrm{Content} + (w_I + w_U) \cdot \tilde{I}$。$\tilde{I}$ は「学生が興味を示した募集たちと P の行動の近さ（CF_P）の平均」。PR274 のとおり、候補を選ぶ段階では片方で足りるため |
| PR283 | 承認 | 近さの定義（割り引きの重み、応募理由の近さ、√W による正規化、信頼度）は今の設計書のまま使う。I・U は、似たリストの相手だけでなく、興味を示した相手すべてで平均する。自分自身（P 自身、S 自身）は除く |
| PR288 | 承認 | Content は SQL だけで計算する。組み合わせ（募集×学生、学生どうし、募集どうし）ごとに1つずつ書き、Ruby 版は持たない。どの組み合わせも数千〜10万件の相手について計算する場面があり SQL 版は必ず要るので、Ruby 版も持つと同じ計算が2通りになるため |
| PR280 | 開発者の案で承認 | おすすめ順は、群（条件に合う・合わない）ごとに、上位100件を f の高い順、101件目以降を新着順。企業の学生検索には新着順がないので「最終活動が新しい順」 |
| PR285 | 承認 | 似たリストのテーブル（似た学生・似た募集）をやめ、スカウト後・応募完了のポップアップと、企業への通知も、その場で計算する（0.1〜0.6秒） |

### 3-2. 保持するデータと更新の方法

| 番号 | 結果 | 内容 |
| --- | --- | --- |
| PR275 | PR282 に含めて承認 | 学生どうしの共通数を保存しない（最悪2億行）。リランキングで要る分は、その場で数千行から数える |
| PR276 | 承認 | 更新は、足し込み（+1）ではなく、影響を受ける値を元データから数え直して上書きする。+1 は何度実行しても同じ結果にならない（冪等でない）ので、ジョブの再実行で数が二重になり、ずれを直す手段がないため。スカウトへのマッチも、今までどおり応募と同じく興味として数える |
| PR286 | 承認 | 学生・募集ごとの Content 用の項目数（職種の中分類・大分類、工程、技術、業界）を集計の表に持ち、プロフィール・募集の保存と同じトランザクションで保存し直す。ジャカード係数の分母に相手の項目数が要り、検索のたびに数えると約150万行を読むことになるため |
| PR279 | 設けない | 1人あたりの応募数・1募集あたりの応募者数に、システムの上限は設けない |
| PR287 | 承認 | 利用者の応募は制限しないまま、計算に使う興味の数だけに上限を設ける（募集ごとに直近200人、学生ごとに直近20件）。件数と self_weight は全員分で正確に数える |

- 開発者は「PR279 それでいいと思います」と答えたが、PR279 はその前に「しなくてよい」と答えていた。そのとき相談していたのは PR287 だったので、PR287 の承認として扱い、開発者に伝えた
- 応募・マッチのジョブで行うこと：件数の数え直し、応募された募集に興味を示した全学生の self_weight の数え直し（約4,000行）、応募した学生が興味を示した全募集の self_weight の数え直し（約4,000行）、通知。0.02〜0.1秒（通知を含めて0.1〜0.4秒）。これまでの約0.8秒から軽くなった
- 影響を受ける値をすべて数え直すので、「応募のたびには追わないずれ」がなくなり、**夜間の作り直しは不要**になった（「できたらする」から外した）
- プロフィール・募集の保存では、推薦のジョブを動かさない。企業のプロフィール保存では推薦の処理は何もしない
- データベースは 44 → 42テーブル

### 3-4. AI が補ったこと

- 「興味を示した日時」（上限の新しい順の基準）は、応募は応募した日時、スカウトはマッチした日時
- 上限を超える募集・学生が関わるときだけ、計算した値は式の近似になる。同じ組の値が、どちら側から数えたかでわずかに変わることがある
- PR280 を群ごとにしたので、企業の学生検索の内容の経路の1,000人と、上位100件の選び方も群ごとにした
- 興味が減る出来事（やりとりの削除、退会）は今回作らない。作るときは応募・マッチと同じ手順で数え直せば済む

### 3-5. 見積もり（運用規模のいちばん重い場合）

| 場面 | 時間の目安 |
| --- | --- |
| 企業の学生検索のおすすめ順 | 約0.4〜1.0秒 |
| 学生の募集一覧のおすすめ順 | 約0.2〜0.6秒 |
| スカウト後のポップアップ（似た学生） | 約0.3〜0.6秒 |
| 応募完了のポップアップ（似た募集） | 約0.1〜0.3秒 |
| 応募・マッチのジョブ | 約0.02〜0.1秒（通知を含めて0.1〜0.4秒） |

- 途中で、学生の募集検索の見積もりを「約0.3〜0.7秒」と伝えていたが、リランキングで相手の学生が延べ2万人になることを見落としていた。その Content をデータベースで計算する形にして、約0.2〜0.6秒に直した
- 計算による目安なので、実際の速さはダミーデータを大量に作るコマンドで実測して確かめる（技術構成.md の 9-4-1）
